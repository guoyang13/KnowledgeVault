# 信息的表示和处理

本章是计算机系统的地基：所有数据最终都是位，但不同解释规则会让同一串位变成不同含义。

## 核心问题

计算机如何用有限的位表示整数、浮点数、字符和地址？为什么会出现溢出、精度丢失和类型转换陷阱？

## 位、字节和字

- `bit`：最小信息单位，只能是 0 或 1。
- `byte`：字节，通常是 8 个 bit。
- `word`：字，机器一次自然处理的数据大小，常见 32 位或 64 位。

位模式没有天然语义，语义由类型和解释方式决定。

## 地址和字节序

多字节对象需要决定字节排列顺序。

以 `0x12345678` 为例：

```text
大端：12 34 56 78
小端：78 56 34 12
```

- 大端：高位字节放低地址，更符合人类读数字的顺序，常用于网络字节序。
- 小端：低位字节放低地址，x86 常用，便于低位访问和某些本地运算。

注意：

> 大端和小端没有绝对谁更高级，关键是通信双方必须约定一致。

## 整数表示

常见整数表示：

- 无符号整数：所有位都表示非负数值。
- 有符号整数：通常使用补码表示。

补码的核心特点：

- 最高位既参与数值，又承担符号意义。
- 表示范围不对称。
- 对 w 位有符号整数，范围通常是 `-2^(w-1)` 到 `2^(w-1)-1`。

例如 8 位补码：

```text
00000000 = 0
01111111 = 127
10000000 = -128
11111111 = -1
```

## 为什么补码重要

补码让加减法可以统一为同一套硬件运算。CPU 不需要为正数和负数设计两套完全不同的加法器。

这也是为什么：

```text
-1 的补码通常是全 1
```

位运算、溢出判断、符号扩展都和补码密切相关。

## 类型转换陷阱

在 C 语言里，有符号数和无符号数混合运算时，经常发生隐式转换。底层位模式可能不变，但解释方式变了，结果就会非常反直觉。

Java 相对更安全一些，但仍然要理解：

- `byte`、`short` 运算会提升为 `int`。
- `char` 是无符号 16 位值。
- 整数溢出不会自动报错。
- `long` 和 `int` 混用时要注意范围。

## 整数溢出

有限位宽意味着整数范围有限。

例如 32 位 `int`：

```text
Integer.MAX_VALUE + 1 = Integer.MIN_VALUE
```

这不是数学错误，而是有限位宽下的回绕。

后端开发中的影响：

- 金额、库存、积分、计数器不能盲目使用 `int`。
- ID、时间戳、累加值要考虑范围。
- 分页计算 `page * size` 可能溢出。

## 位运算

常见位运算：

- `&`：按位与，常用于掩码。
- `|`：按位或，常用于设置标志位。
- `^`：按位异或，常用于翻转或差异检测。
- `~`：按位取反。
- `<<`：左移，通常相当于乘以 2 的幂，但要注意溢出。
- `>>`：算术右移，保留符号位。
- `>>>`：Java 的逻辑右移，高位补 0。

## 浮点数表示

现代计算机常用 IEEE 754 表示浮点数。

浮点数大致拆成：

- 符号位。
- 指数字段。
- 小数字段。

它表示的是近似实数，不是精确实数。

所以：

```java
0.1 + 0.2 != 0.3
```

这不是 Java 特有问题，而是二进制浮点数无法精确表示很多十进制小数。

## 浮点数特殊值

IEEE 754 支持：

- 正无穷和负无穷。
- `NaN`，表示不是一个数。
- 正零和负零。
- 规格化数和非规格化数。

工程上要注意：

- 不要用浮点数表示金额。
- 浮点比较不要直接用 `==`。
- 聚合计算要考虑舍入误差。

## Java 工程师关联

- `int` 溢出、`long` 溢出会导致线上隐蔽 bug。
- 金额使用 `BigDecimal`，不要使用 `double`。
- 哈希、位图、权限标记、Bloom Filter 都依赖位运算。
- 网络协议、二进制文件、Redis bitmap、MQ 二进制消息都涉及字节序。
- 排查序列化问题时，要能区分“值错了”还是“解释字节的方式错了”。

## 本章一句话

计算机中的数不是数学中的无限精确数，而是在有限位宽和特定编码规则下的近似表示。
