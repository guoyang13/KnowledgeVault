# 优化程序性能

本章讨论如何从机器执行模型理解性能优化：优化不是凭感觉改代码，而是减少无效工作、减少数据依赖、提高局部性和并行性。

## 核心问题

为什么两个时间复杂度相同的程序，实际运行时间可能差很多？

因为真实机器还受到这些因素影响：

- 指令数量。
- 数据依赖。
- 分支预测。
- 缓存命中率。
- 内存访问模式。
- 编译器能否安全优化。

## 编译器优化的边界

编译器很强，但不能随意改变程序语义。

它经常受限于：

- 指针或引用别名。
- 函数调用是否有副作用。
- 内存可见性。
- 异常行为。
- 动态分派。

Java JIT 也类似。它需要根据运行时类型、逃逸分析、内联条件、类层次结构等信息判断能否优化。

## 低效循环

常见低效来源：

- 循环里重复计算不变表达式。
- 每轮都调用可提前计算的方法。
- 频繁访问内存而不是复用局部变量。
- 循环体存在强数据依赖。

例子：

```java
for (int i = 0; i < list.size(); i++) {
    // 如果 size() 很贵，就会被重复调用
}
```

现代 JVM 可能优化一部分情况，但工程上仍应写出容易优化的代码。

## 每元素周期数 CPE

CPE 用来衡量处理每个元素平均需要多少 CPU 周期。

它适合分析数组处理、循环累加、批量计算等场景。

对后端开发来说，可以类比为：

- 每条记录处理耗时。
- 每个订单处理耗时。
- 每个消息消费耗时。

关注单位工作成本，比只看总耗时更容易定位瓶颈。

## 循环展开

循环展开通过减少循环控制开销和暴露更多并行机会来提升性能。

例如每次处理 1 个元素改成每次处理 4 个元素。

收益：

- 减少分支判断次数。
- 给 CPU 更多独立指令。
- 方便编译器调度。

风险：

- 代码变复杂。
- 指令缓存压力增加。
- 现代编译器/JIT 可能已经自动完成。

## 指令级并行

现代处理器可以同时推进多条不互相依赖的指令。

如果代码存在链式依赖：

```text
a1 -> a2 -> a3 -> a4
```

CPU 很难并行。

如果代码拆成多个独立累加器：

```text
a1 -> a2
b1 -> b2
c1 -> c2
```

CPU 更容易并行执行。

## 内存性能

很多程序不是 CPU 算不动，而是数据供不上。

内存访问慢的原因：

- 缓存未命中。
- 随机访问破坏空间局部性。
- 数据结构分散。
- 多线程竞争同一缓存行。

因此，数组通常比链表更缓存友好。

## 性能优化基本步骤

1. 先测量，不要猜。
2. 找到热点路径。
3. 判断瓶颈是 CPU、内存、I/O、锁、GC 还是数据库。
4. 优先优化占比最高的部分。
5. 每次修改后重新验证。

常用工具：

- Java：JFR、async-profiler、Arthas、JMH。
- Linux：top、perf、strace、iostat、vmstat。
- 应用侧：日志、指标、链路追踪。

## Java 工程师关联

- 不要只看大 O，常数、缓存、分支、对象分配都重要。
- 热点代码里减少不必要对象创建。
- 批量处理时注意数组/列表访问模式。
- 慎用反射、动态代理、过深调用链。
- 性能测试要预热 JVM，区分解释执行、JIT 编译和稳定状态。

## 本章一句话

性能优化的本质是让机器少做无效工作，并让 CPU、缓存、内存和编译器更容易协同。
