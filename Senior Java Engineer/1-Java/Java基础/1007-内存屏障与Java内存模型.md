## 一句话概括

**内存屏障（Memory Barrier / Fence）** 是编译器或 CPU 插入的约束，**限制内存访问重排**并**保证多线程可见性**；JMM 通过 `volatile`、`synchronized`、CAS 等语法建立 happens-before，HotSpot 在底层翻译成 **MemBar 节点 + CPU 屏障指令**。

---

# Part I：是什么

## 1. 定义

内存屏障告诉 CPU 和编译器：

```text
屏障之前的内存访问 与  屏障之后的内存访问
  → 不能随意重排
  → 必要时刷写 Store Buffer / 同步缓存，让其他核看见
```

没有屏障时，每个核、编译器都可能为性能 **乱序执行、延迟写回**；并发下会出现「别的线程看见的顺序」和「代码书写顺序」不一致。

## 2. 与 GC 读/写屏障区分（易混）

| 维度 | 内存屏障 | GC 读/写屏障 |
|------|----------|--------------|
| 目的 | 多线程 **可见性 + 有序性** | 垃圾回收 **正确性** |
| 谁插入 | 编译器 / CPU（JMM 语义） | JVM GC 子系统 |
| 触发 | `volatile`、锁、CAS 等 | 堆上读/写 **对象引用** |
| 典型场景 | `flag=true` 后他线程看见 `x=1` | G1 维护 RSet、ZGC 修正染色指针 |

```text
内存屏障：  线程 A 写 x=1 ──[StoreLoad]── volatile flag=true
            线程 B 读 flag ── 必须看到 x=1

GC 写屏障： obj.field = other ── 记录到 RSet，供 Young GC 扫描
GC 读屏障： ref = obj.field ── 检查染色指针，修正已移动对象
```

名字都带「屏障」，**解决的问题完全不同**。本篇只讲 **内存屏障 + JMM**。

## 3. 四种基本类型

| 类型 | 约束（直观） |
|------|----------------|
| **LoadLoad** | 屏障前的读，不能排到屏障后的读后面 |
| **StoreStore** | 屏障前的写，不能排到屏障后的写后面 |
| **LoadStore** | 屏障前的读，不能排到屏障后的写后面 |
| **StoreLoad** | 屏障前的写，不能排到屏障后的读后面（**最强、最贵**） |

**Full Fence（全屏障）**：四种都满足。

**StoreLoad** 通常最贵：往往要清空 **Store Buffer** 并参与缓存同步，相当于「写全可见后再读最新的」。

# Part II：为什么需要

## 4. 编译器会重排

JIT（C2）会做指令调度，例如：

```java
a = 1;
flag = true;   // 意图：通知其他线程
b = 2;
```

编译器可能把 `b = 2` 挪到 `flag = true` 之前。单线程结果不变，但其他线程看到 `flag==true` 时 `b` 可能仍为 0。

## 5. CPU 会乱序执行

现代 CPU 有：

| 机制 | 影响 |
|------|------|
| **写缓冲（Store Buffer）** | 写先排队，不立刻进缓存 |
| **乱序执行** | 后一条指令不等前一条完成 |
| **多级缓存** | 每核 L1/L2，读到的可能是旧值 |

线程 A 写入后，线程 B **不一定立刻看见**，也不一定按代码顺序看见。

## 6. 缓存一致性 ≠ 程序顺序

MESI 等协议保证 **最终** 各核收敛到同一值，但不保证：

- **何时** 可见
- 与 **源代码书写顺序** 一致

双重检查锁失效、未完全构造对象被发布等 bug，多源于此。

# Part III：JMM 映射

JMM（Java Memory Model）不让你手写屏障，而是用 **happens-before** 规则；满足规则时 JVM 插入对应屏障。

## 7. happens-before 核心规则（节选）

| 规则 | 含义 |
|------|------|
| 程序顺序 | 同线程内，前面的操作 hb 后面的操作 |
| 监视器锁 | `unlock` hb 后续对同一锁的 `lock` |
| `volatile` | 写 hb 后续对同一变量的读 |
| 线程启动 | `Thread.start()` hb 线程内动作 |
| 线程终止 | 线程内动作 hb `Thread.join()` 返回 |
| 传递性 | A hb B，B hb C → A hb C |

## 8. `volatile` 的屏障语义

```java
// 线程 A
x = 42;
ready = true;  // volatile 写

// 线程 B
if (ready) {   // volatile 读
    use(x);    // 保证看到 x == 42
}
```

等价屏障组合：

| 操作 | 插入屏障 |
|------|----------|
| **volatile 写** 前 | StoreStore（普通写不能跑到 volatile 写后） |
| **volatile 写** 后 | StoreLoad（volatile 写不能跑到后续读前） |
| **volatile 读** 后 | LoadLoad + LoadStore（volatile 读不能跑到后续读写前） |

**结论**：volatile 写 **之前** 的普通写，对 **之后** 的 volatile 读可见。

## 9. `synchronized`

| 时机 | 屏障语义 |
|------|----------|
| **进入** monitor | LoadLoad + LoadStore（锁内读能看到释放前的写） |
| **退出** monitor | StoreStore + StoreLoad（锁内写对后续获锁线程可见） |

锁 = **互斥** + **内存同步**；不仅防并发写，还建立可见性。

## 10. CAS / `Atomic*` / `VarHandle`

- `compareAndSet` 成功：常带 **acquire** 语义
- 锁释放、`volatile` 写：常带 **release** 语义

| 术语 | 含义 |
|------|------|
| **Acquire** | 后续读写不能跑到它前面 |
| **Release** | 前面读写不能跑到它后面 |

## 11. 经典案例：双重检查锁（DCL）

错误写法：

```java
if (instance == null) {
    synchronized (Singleton.class) {
        if (instance == null) {
            instance = new Singleton(); // 可能被重排！
        }
    }
}
```

`new Singleton()` 字节码大致：

```text
1. 分配内存
2. 调用构造器
3. 引用赋给 instance
```

CPU/编译器可能 **3 先于 2** → 他线程看到 `instance != null` 但对象未构造完。

**修复**：`instance` 声明为 `volatile`（JDK5+ JMM 保证正确 DCL），或静态内部类 / 枚举单例。

# Part IV：怎么实现

## 12. 三层实现栈

```text
Java 代码 (volatile / synchronized / CAS)
        ↓
  编译器屏障 — 禁止 JIT 重排
        ↓
  CPU 内存屏障指令 — 约束处理器与缓存
        ↓
  缓存一致性 (MESI) — 多核数据同步
```

## 13. HotSpot 中的 MemBar

C2 在需要 JMM 语义处插入 IR 节点，例如：

| 节点 | 用途 |
|------|------|
| `MemBarVolatile` | volatile 读写 |
| `MemBarAcquire` | 锁入口、CAS 成功后的读侧 |
| `MemBarRelease` | 锁出口、volatile 写 |

## 14. x86 / x64

x86 对单核基本是 **TSO（Total Store Order）**，较强：

| 重排类型 | 硬件行为 |
|----------|----------|
| 写→写、读→读、读→写 | 大多不乱序 |
| **写→读** | **可能乱序**（Store Buffer） |

因此 x86 上 LoadLoad / StoreStore 常只需 **编译器屏障（no-op）**；**StoreLoad** 仍需真指令：

```asm
lock addl $0, 0(%rsp)   ; 常见：lock 刷 Store Buffer
; 或
mfence                  ; 全屏障
```

## 15. ARM / Apple Silicon

ARM 是 **弱内存模型**，乱序更自由，需显式指令：

| 指令 | 作用 |
|------|------|
| `DMB` | 按类型限制读写重排 |
| `DSB` | 更强，等前面访问完成 |
| `ISB` | 刷新指令流水线 |

`volatile` / `synchronized` 在 ARM 上通常生成 **更多真实硬件屏障**，开销常略高于 x86。

## 16. 实现对照表

| 平台 | volatile 写后 | synchronized 退出 |
|------|---------------|-------------------|
| x86 | 多为 `lock` 或轻量 fence | `lock` + unlock 语义 |
| ARM | `dmb ish` 等 | `dmb` + 原子释放 |

# Part V：工程实践

## 17. 何时需要关心

| 场景 | 是否需要显式理解屏障 |
|------|----------------------|
| 业务 CRUD | 通常否，用 `ConcurrentHashMap` 等即可 |
| 单例、标志位、状态机 | **是**，`volatile` / 锁顺序 |
| 无锁队列、自定义池 | **是**，acquire/release 配对 |
| 高频 `AtomicLong` 竞争 | 注意 CAS 与伪共享 |

## 18. 伪共享（False Sharing）

两线程修改 **同一缓存行** 内不同变量 → 缓存行来回失效，屏障开销被放大。

缓解：

- 字段 padding
- JDK 8+ `@sun.misc.Contended` / `jdk.internal.vm.annotation.Contended`
- `LongAdder` 代替高频 `AtomicLong`

## 19. 性能要点

| 因素 | 影响 |
|------|------|
| StoreLoad / `mfence` | 最贵 |
| 过度 `volatile` | 每次读写付可见性成本 |
| ARM vs x86 | ARM 屏障指令更多 |
| 锁竞争 | synchronized 退出含 StoreLoad |

优化原则：

- 优先高层抽象（`java.util.concurrent`）
- 能局部同步就不全局 `volatile`
- 计数用 `LongAdder`，状态发布用 `volatile` 或 `AtomicReference`

## 20. 与 GC 专题的交叉阅读


## 面试速记

1. **是什么**：限制重排 + 保证可见性的 CPU/编译器约束。
2. **为什么**：编译器优化、Store Buffer、多核缓存导致乱序与延迟可见。
3. **四种**：LoadLoad、StoreStore、LoadStore、**StoreLoad**（最贵）。
4. **volatile**：写前 StoreStore，写后 StoreLoad；读后 LoadLoad+LoadStore。
5. **synchronized**：入口 acquire，出口 release + StoreLoad。
6. **x86**：写→读可能乱序；StoreLoad 要真指令。
7. **ARM**：弱模型，DMB/DSB 更常见。
8. **≠ GC 屏障**：JMM 管线程可见性；GC 屏障管回收正确性。
