## 一句话概括

**TCCL（Thread Context ClassLoader）** 是每个 `Thread` 上绑定的 `ClassLoader` **引用**，表示「这条线程默认用哪个 ClassLoader 找类和资源」。它 **不是** 新的 ClassLoader 类型，而是 **线程级别的指针**。SPI/JDBC 靠 TCCL 让 Bootstrap 加载的代码，反向使用应用层 ClassLoader。

---

## 1. TCCL 是什么

```java
// 获取
ClassLoader cl = Thread.currentThread().getContextClassLoader();

// 设置
Thread.currentThread().setContextClassLoader(myClassLoader);
```

```text
Thread 对象
├── name, target, ...
└── contextClassLoader  →  指向某个已存在的 ClassLoader 实例（引用）
```

| 概念 | 说明 |
|------|------|
| **ClassLoader 层次** | Bootstrap → Platform → App → 自定义（固定父子委派链） |
| **TCCL** | 每条线程独立，可指向链上任意一层（通常是应用层） |

---

## 2. 为什么需要 TCCL

### 2.1 双亲委派的局限

```text
Bootstrap 加载 DriverManager
    → 无法向下委派到 AppClassLoader 加载 mysql-connector.jar 里的类
```

接口/调用方在 JDK（高层），实现在应用 jar（低层），需要 **反向** 借用应用 ClassLoader。

### 2.2 TCCL 的解法

```java
// ServiceLoader.load 无参版本（JDK 源码）
ClassLoader cl = Thread.currentThread().getContextClassLoader();
ServiceLoader.load(service, cl);

// 等价于
Class.forName(implName, false, tccl);
```

详见 [[1002-SPI机制]]。

### 2.3 与「打破双亲委派」的区别

| | 双亲委派 | TCCL |
|--|----------|------|
| 机制 | `loadClass` 先父后子 | 线程上挂 ClassLoader 引用 |
| 方向 | 自下而上 | 高层代码 **主动指定** 用哪个 loader |
| 是否改变加载器树 | 否 | 否 |

---

## 3. TCCL 什么时候被设置

### 3.1 不是单独 new 出来的

TCCL 是 Thread 字段，在 **线程创建/启动时赋值**，指向已有的 ClassLoader 实例。

### 3.2 主线程（main）

```text
JVM 启动 → 创建 main 线程
    → Launcher 将 TCCL 设为 AppClassLoader 或 LaunchedURLClassLoader
    → 执行 main()
```

### 3.3 普通 new Thread()

```java
// JDK Thread 构造逻辑（简化）
this.contextClassLoader = Thread.currentThread().getContextClassLoader();
// 继承「创建者线程」在 new Thread() 时刻的 TCCL
```

```text
主线程 TCCL = LaunchedURLClassLoader
    → new Thread(task).start()
    → 子线程 TCCL = LaunchedURLClassLoader  ✓
```

**继承时机：线程对象 new 出来的那一刻**（不是 start()，不是任务执行时）。

### 3.4 线程池 Worker 线程

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
// 4 个 Worker 在「创建池时当前线程」上 new 出来
// Worker.TCCL = 创建池那一刻的 TCCL，之后长期不变
```

### 3.5 各环境典型 TCCL

| 环境 | TCCL 通常是谁 | 谁设置 |
|------|----------------|--------|
| `main` 普通启动 | AppClassLoader | JVM / Launcher |
| Spring Boot `java -jar` | LaunchedURLClassLoader | JarLauncher |
| Tomcat HTTP 请求线程 | WebappClassLoader | 容器 |
| 线程池 Worker（启动时创建） | 创建池时继承的 CL | 继承自 main 等 |
| `getContextClassLoader()` 为 null | 回退 SystemClassLoader | JDK 兜底 |

## 4. 谁在使用 TCCL

| 组件 | 用法 |
|------|------|
| `ServiceLoader.load()` | 默认 TCCL 扫 `META-INF/services` |
| `DriverManager` | JDBC 驱动 SPI |
| JNDI / JAXP 等 | 加载应用提供的实现 |
| Spring | 资源加载、部分类加载 |
| Tomcat | Web 应用隔离 |

## 5. 为什么异步后 TCCL「不对」

### 5.1 核心原因

> **TCCL 在线程「出生」时定下来；线程池 Worker 很早就创建，执行 submit 的任务时不会自动换成提交者线程的 TCCL。**

```text
【你以为】
提交任务的线程 TCCL  →  自动传给  →  执行任务的线程

【实际上】
Worker.TCCL = Worker 被 new 时那一刻的 TCCL（通常很早）
```

### 5.2 典型场景：Tomcat + 线程池

```text
【应用启动】
main TCCL = LaunchedURLClassLoader
    → newFixedThreadPool(4)
    → Worker.TCCL = LaunchedURLClassLoader

【请求到来】
Tomcat 请求线程 TCCL = WebappClassLoader
    → pool.submit(() -> ServiceLoader.load(...))
    → 任务在 Worker 上执行
    → Worker.TCCL 仍是 LaunchedURLClassLoader  ✗
```

**多数情况不是 TCCL「丢失」，而是用了错误的 ClassLoader。**

### 5.3 其他场景

| 场景 | 问题 |
|------|------|
| `CompletableFuture.runAsync` | 默认 ForkJoinPool，Worker TCCL 常为 AppClassLoader |
| 池在启动时创建、任务在请求时提交 | Worker TCCL 与请求线程不一致 |
| 有人 `setContextClassLoader(null)` | `getContextClassLoader()` 回退系统 CL |

### 5.4 与 InheritableThreadLocal 对比

| | TCCL | InheritableThreadLocal |
|--|------|------------------------|
| 继承时机 | 线程 new 时复制一次 | 线程 new 时复制一次 |
| submit 到已存在 Worker | **不**更新 | **不**更新 |

两者都不会在 `pool.submit(task)` 时把提交者线程的值传给已存在的 Worker。

### 5.5 为什么同步代码往往正常

```text
Tomcat 请求进入 → 当前线程 TCCL = WebappClassLoader → 同步 SPI 正常
改成 @Async / 线程池 → 换线程 → TCCL 可能不对 → 异步才暴露问题
```

### 5.6 深度案例：Spring Boot 内嵌 Tomcat + FixedThreadPool

> `submit` 只传 Runnable，**不会**把提交者线程的 TCCL 复制给 Worker。

#### 5.6.1 核心矛盾（一句话）

```text
pool.submit() 把任务交给 Worker 执行
但不会把「提交任务那条线程」的 TCCL 带过去
```

| 线程 | TCCL |
|------|------|
| Tomcat 请求线程（提交任务） | WebappClassLoader |
| 业务池 Worker（执行任务） | 启动时定格的 LaunchedURLClassLoader |

---

#### 5.6.2 【应用启动】时间线

**① `java -jar` 启动**

```text
JVM 加载 JarLauncher（AppClassLoader）
    ↓
JarLauncher 创建 LaunchedURLClassLoader，加载 BOOT-INF
    ↓
反射调用 SpringApplication.main()
    ↓
main 线程 TCCL = LaunchedURLClassLoader
```

此时只有 main 线程，**还没有 HTTP 请求线程**。

**② Spring Boot 启动内嵌 Tomcat**

```text
SpringApplication.run()
    ↓
创建 Embedded Tomcat
    ↓
创建 TomcatEmbeddedWebappClassLoader（WebappClassLoader 子类）
    ↓
Tomcat 监听 8080（WebappClassLoader 已存在，但 HTTP 线程尚未处理业务请求）
```

**③ 启动阶段创建业务线程池**

```java
@Bean
public ExecutorService pool() {
    return Executors.newFixedThreadPool(4);  // Spring 启动时执行
}
```

```text
执行 @Bean 时，当前线程 = main / Spring 启动线程，TCCL = LaunchedURLClassLoader
    ↓
newFixedThreadPool(4) 内部 new 4 个 Worker（此时创建，不是等有任务才创建）
    ↓
每个 Worker 构造时：
    contextClassLoader = 当前线程.getContextClassLoader()
                       = LaunchedURLClassLoader
    ↓
Worker TCCL 永久「定格」在启动这一刻
```

---

#### 5.6.3 【请求到来】时间线

**① Tomcat 收到 HTTP 请求**

```text
从 Tomcat HTTP 线程池取线程：http-nio-8080-exec-3
    ↓
处理前设置：Thread.setContextClassLoader(webappClassLoader)
    ↓
该请求线程 TCCL = WebappClassLoader
```

**② 同步 Controller（正常）**

```java
@GetMapping("/sync")
public String sync() {
    // 线程 http-nio-8080-exec-3，TCCL = WebappClassLoader ✓
    ServiceLoader.load(Driver.class);
    return "ok";
}
```

**③ 异步 submit（出问题）**

```java
@GetMapping("/async")
public String async() {
    // ① Tomcat 请求线程，TCCL = WebappClassLoader
    pool.submit(() -> {
        // ③ Worker 线程，TCCL 仍是 LaunchedURLClassLoader ✗
        ServiceLoader.load(Driver.class);
    });
    // ② submit 只把 lambda 放入队列，不复制 TCCL
    return "ok";
}
```

```text
T1  启动：main TCCL = LaunchedURLClassLoader
T2  newFixedThreadPool → Worker TCCL = LaunchedURLClassLoader（固定）
T3  HTTP 请求 → Tomcat 线程 TCCL = WebappClassLoader
T4  pool.submit(task)
T5  Worker 执行 task → 仍用 T2 的 TCCL
```

---

#### 5.6.4 三套线程池（易混）

```text
┌─ 1. main / Spring 启动线程 ─────────────────────────┐
│  TCCL = LaunchedURLClassLoader                      │
│  → 在这里 newFixedThreadPool(4)                     │
│  → 业务 Worker-1~4 TCCL = LaunchedURLClassLoader    │
└─────────────────────────────────────────────────────┘

┌─ 2. Tomcat HTTP 线程池（容器自己的）─────────────────┐
│  http-nio-8080-exec-*                               │
│  TCCL = WebappClassLoader（Tomcat 每请求设置）       │
│  → 同步 Controller 在这里跑 ✓                        │
└─────────────────────────────────────────────────────┘

┌─ 3. 业务 FixedThreadPool Worker ────────────────────┐
│  pool-thread-1 ~ 4                                  │
│  TCCL = 启动时继承的 LaunchedURLClassLoader          │
│  → @Async / submit 在这里跑                         │
└─────────────────────────────────────────────────────┘
```

**Tomcat 线程池 ≠ 业务 FixedThreadPool**，TCCL 各管各的。

---

#### 5.6.5 fat jar vs 外置 WAR：问题严重程度

| 部署方式 | LaunchedURL vs Webapp | 异步 SPI 表现 |
|----------|----------------------|---------------|
| Spring Boot fat jar + 内嵌 Tomcat | 父子关系，classpath **高度重叠** | 有时 **碰巧成功**，问题不明显 |
| 外置 Tomcat 部署 WAR | Webapp 见 WEB-INF/lib，App **不见** | **几乎必挂**（ClassNotFound / No suitable driver） |
| 任意场景 | 两个不同 ClassLoader 实例 | 仍可能 `ClassCastException: A cannot be cast to A` |

---

#### 5.6.6 可运行的验证代码

```java
@RestController
public class TcclDemoController {

    private final ExecutorService pool = Executors.newFixedThreadPool(4);

    @GetMapping("/tccl-demo")
    public String demo() {
        log.info("request thread: {}, TCCL: {}",
            Thread.currentThread().getName(),
            Thread.currentThread().getContextClassLoader());
        // → http-nio-8080-exec-1, TomcatEmbeddedWebappClassLoader

        pool.submit(() -> {
            log.info("worker thread: {}, TCCL: {}",
                Thread.currentThread().getName(),
                Thread.currentThread().getContextClassLoader());
            // → pool-1-thread-1, LaunchedURLClassLoader（若池在启动时创建）
        });
        return "submitted";
    }

    @GetMapping("/tccl-fixed")
    public String fixed() {
        ClassLoader cl = Thread.currentThread().getContextClassLoader();
        pool.submit(() -> {
            Thread.currentThread().setContextClassLoader(cl);
            ServiceLoader.load(Driver.class);
        });
        return "ok";
    }
}
```

#### 5.6.7 常见误解

| 误解 | 事实 |
|------|------|
| submit 会把 TCCL 传给 Worker | **不会**，只传 Runnable |
| Worker 每次执行任务会刷新 TCCL | **不会**，除非任务内 `setContextClassLoader` |
| Tomcat 会改业务线程池的 TCCL | **不会**，只改自己的 HTTP 线程 |
| fat jar 一定不会有问题 | **可能较轻**，但 ClassLoader 不一致仍存在 |
| 是 TCCL「丢失」 | 多数是 **用了错误的 ClassLoader** |

## 6. 用错 ClassLoader 为什么导致加载异常

### 6.1 根本原因

**每个 ClassLoader 只能看到自己 classpath 上的类和资源。**

```text
WebappClassLoader 可见：WEB-INF/classes + WEB-INF/lib
AppClassLoader 可见：    应用 main classpath（可能不含 WEB-INF/lib）
```

`loader.getResources()` / `Class.forName(..., loader)` **只扫该 loader 可见路径**。

### 6.2 会出现的异常

| 异常/现象 | 原因 |
|-----------|------|
| `ClassNotFoundException` | 目标 jar 不在该 ClassLoader 的 classpath |
| `ServiceConfigurationError` | SPI 配置扫到但 `Class.forName` 失败 |
| `No suitable driver found` | JDBC SPI 未加载到 Driver 实现 |
| SPI 迭代为空 | `getResources(META-INF/services/...)` 返回空 |
| `ClassCastException: A cannot be cast to A` | 同名类被 **不同 ClassLoader** 各加载一份 |
| `LinkageError`（较少） | 跨 loader 边界使用类 |

### 6.3 SPI 错误路径示例

```text
TCCL = AppClassLoader（Worker）
    ↓
getResources("META-INF/services/java.sql.Driver") → 空（jar 在 WEB-INF/lib）
    ↓
无 Provider / ClassNotFoundException
```

### 6.4 ClassLoader 可见性对照

| ClassLoader | 典型可见范围 |
|-------------|--------------|
| Bootstrap | `java.*` 核心类 |
| AppClassLoader | main classpath |
| WebappClassLoader | 当前 WAR 的 WEB-INF |
| LaunchedURLClassLoader | BOOT-INF/classes + lib |

## 7. 正确做法

### 7.1 提交任务时捕获 TCCL，执行前设置

```java
ClassLoader cl = Thread.currentThread().getContextClassLoader();
pool.submit(() -> {
    Thread.currentThread().setContextClassLoader(cl);
    try {
        ServiceLoader.load(MyService.class);
    } finally {
        // 可选：恢复 Worker 原 TCCL，避免污染后续任务
    }
});
```

### 7.2 显式传 ClassLoader（更稳）

```java
ServiceLoader.load(MyService.class, capturedClassLoader);
Class.forName(name, true, capturedClassLoader);
```

### 7.3 框架装饰器

- Spring：`TaskDecorator`（`@Async`）
- Tomcat：部分异步包装会设 TCCL
- 思路同 `DelegatingSecurityContextRunnable`

### 7.4 JDK 21 虚拟线程（补充）

```java
Thread.startVirtualThread(() -> { ... });
// 虚拟线程 TCCL = 调用 startVirtualThread 时当前线程的 TCCL

Executors.newVirtualThreadPerTaskExecutor()
// 每个任务新虚拟线程，TCCL 继承自 submit 时线程 → 更接近预期
```

## 9. 整体关系图

```text
【结构层次 - 父子委派链】（启动时确定，固定）
Bootstrap → Platform → AppClassLoader → LaunchedURLClassLoader

【线程上下文 - TCCL】（按线程可变）
Thread-1 TCCL = WebappClassLoader
Thread-2 TCCL = LaunchedURLClassLoader
Thread-3 TCCL = AppClassLoader

SPI 调用链：
DriverManager（Bootstrap）
    → getContextClassLoader()
    → ServiceLoader.load(Driver.class, tccl)
    → tccl.getResources + Class.forName(..., tccl)
```

## 10. 面试速记

1. **TCCL** = 线程绑定的 ClassLoader 引用，非新 ClassLoader 类型。
2. **何时设置**：main 由 JVM 设；子线程在 **new Thread()** 时继承创建者 TCCL。
3. **为何需要**：双亲委派下父加载器无法加载子路径实现，TCCL 反向借用应用 CL。
4. **异步问题**：池 Worker 启动时固定 TCCL，submit 不会更新 → 常用错 CL，非真正「丢失」。
5. **错 CL 后果**：ClassNotFound、SPI 空、No suitable driver、ClassCastException。
6. **解法**：捕获并 `setContextClassLoader`，或显式传 `ClassLoader` 给 `ServiceLoader`。
7. **Tomcat + 业务池**：HTTP 线程 TCCL=WebappClassLoader；启动时创建的池 Worker TCCL=LaunchedURLClassLoader；submit 不复制 TCCL。
