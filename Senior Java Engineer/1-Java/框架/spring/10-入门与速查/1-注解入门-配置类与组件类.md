# 配置类与组件类

> [!abstract] 摘要
> 配置类（Configuration Class）描述“容器中有哪些对象、如何装配”；组件类（Component Class）承载“对象自身的业务或技术职责”。二者最终都会形成 Bean 定义并由同一容器创建，但配置类还会被配置类解析器读取。

## 1. 中英文概念对照

| 中文名 | English Term / Annotation | 主要语义 |
| --- | --- | --- |
| 配置类 | Configuration Class / `@Configuration` | 声明 Bean、导入配置、扫描组件和启用框架能力 |
| 组件类 | Component Class / `@Component` | 标记由 Spring 管理的通用组件 |
| 服务组件 | Service Component / `@Service` | 表达应用或领域服务语义 |
| 持久化组件 | Repository Component / `@Repository` | 表达持久化职责，并可参与异常转换 |
| Web 控制器 | Controller / `@Controller`、`@RestController` | 表达 Web 请求处理职责 |
| Bean 工厂方法 | Bean Factory Method / `@Bean` | 把方法返回对象注册为 Bean |

`@Configuration`、`@Service`、`@Repository` 和 `@Controller` 都具有 `@Component` 元注解，因此都可被组件扫描发现。专用注解的主要价值是**表达角色**，部分注解还会触发额外框架语义。

## 2. 共同点与核心区别

共同点：

- 都可以形成 `BeanDefinition`，再进入 Bean 创建、注入、初始化和销毁流程。
- 都可使用构造器注入、`@Autowired`、`@Value` 等依赖注入能力。
- 都可通过包扫描发现，也可通过 `register(Class<?>)` 显式注册。

| 维度 | 配置类 | 组件类 |
| --- | --- | --- |
| 主要职责 | 定义装配规则 | 承载业务或技术行为 |
| 自身是否成为 Bean | 是 | 是 |
| 是否作为配置候选解析 | 是 | 只有带配置相关注解时才可能成为 Lite 配置候选 |
| 常见产出 | 配置类自身 + 多个 `@Bean` 定义 | 通常是该类自身对应的 Bean |
| 典型内容 | `@Bean`、`@Import`、`@ComponentScan`、`@PropertySource` | 业务方法、端口实现、控制器逻辑 |
| 是否应承担业务逻辑 | 通常不应 | 按组件角色承担 |

`@Import`、`@ComponentScan` 等注解并非语法上只能放在 `@Configuration` 类上；但为了职责清晰，应把装配规则集中在配置类或组合根。

## 3. 配置类如何工作

```java
@Configuration
@ComponentScan("com.example.order")
class OrderConfiguration {

    @Bean
    Clock clock {
        return Clock.systemUTC;
    }
}
```

主流程：

```text
扫描或显式注册 OrderConfiguration
  -> 为配置类注册 BeanDefinition
  -> refresh
  -> ConfigurationClassPostProcessor
  -> ConfigurationClassParser 解析 @Import、@ComponentScan 等
  -> ConfigurationClassBeanDefinitionReader 注册 @Bean 方法
  -> 普通 Bean 创建流程
```

`AnnotatedBeanDefinitionReader` 负责把明确给出的类注册为定义；`ConfigurationClassPostProcessor` 才在 `refresh` 期间解析配置模型。详见 [[2-元数据层-AnnotatedBeanDefinitionReader与组件注册详解]]。

## 4. Full 与 Lite 配置模式

| 模式 | 典型写法 | `@Bean` 方法调用语义 |
| --- | --- | --- |
| Full Configuration | `@Configuration(proxyBeanMethods = true)` | 配置类会被增强，方法间调用可转到容器，维持受管 Bean 语义 |
| Lite Configuration | `@Component` 中含 `@Bean`，或 `@Configuration(proxyBeanMethods = false)` | 普通 Java 方法调用，不拦截方法间调用 |

```java
@Configuration
class FullConfiguration {

    @Bean
    Repository repository {
        return new Repository;
    }

    @Bean
    Service service {
        return new Service(repository);
    }
}
```

Full 模式下，`repository` 的方法间调用会被配置类增强逻辑处理。更清晰、也兼容 Lite 模式的写法是使用方法参数：

```java
@Configuration(proxyBeanMethods = false)
class LiteConfiguration {

    @Bean
    Repository repository {
        return new Repository;
    }

    @Bean
    Service service(Repository repository) {
        return new Service(repository);
    }
}
```

注意：配置类增强用于维持 `@Bean` 方法语义，不等同于基于 Advisor 的 Spring AOP。两者即使都可能使用 CGLIB，目的和调用链也不同。

## 5. 组件类如何工作

```java
@Repository
class JdbcOrderRepository implements OrderRepository {
}

@Service
class OrderService {

    private final OrderRepository repository;

    OrderService(OrderRepository repository) {
        this.repository = repository;
    }
}
```

主流程：

```text
ClassPathBeanDefinitionScanner 发现 stereotype 注解
  -> 注册 BeanDefinition
  -> refresh 末段预实例化非 lazy 单例
  -> getBean
  -> doCreateBean
  -> 依赖注入和初始化
```

没有被扫描或显式注册的普通类，Spring 不会感知；已经注册的非懒加载单例即使无人引用，默认仍会在启动阶段创建。详见 [[2-元数据层-AnnotatedBeanDefinitionReader与组件注册详解#FAQ：类存在但没有被使用，Spring 会怎样处理？]]。

## 6. 选择规则

| 需求 | 使用方式 |
| --- | --- |
| 自己编写且语义明确的业务组件 | `@Service`、`@Repository`、`@Controller` |
| 通用技术组件 | `@Component` |
| 第三方类、构造过程复杂或需要显式组合 | 配置类中的 `@Bean` |
| 批量发现本项目组件 | `@ComponentScan` |
| 导入另一组配置或选择器 | `@Import` |
| 不需要容器管理的值对象或工具对象 | 保持普通 Java 对象，不加组件注解 |

优先让配置类只负责装配，让组件类只负责行为。这样配置可以替换，业务代码也不必知道对象从何而来。

## 7. 常见误区

| 误区 | 修正 |
| --- | --- |
| `@Service` 与 `@Component` 完全不同 | 注册机制接近，`@Service` 主要增加分层语义 |
| `@Configuration` 只是一个普通组件 | 它还会成为配置类解析候选 |
| 所有 `@Bean` 方法都会拦截方法间调用 | 只有 Full 模式具备该语义 |
| 配置类增强就是 Spring AOP | 二者目的、基础设施和拦截模型不同 |
| `register` 会立即解析 `@Bean` | 注册先写入定义，配置解析发生在 `refresh` |
