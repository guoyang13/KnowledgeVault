# 06 异常处理与拦截器

[[05-Controller返回值处理|上一篇：Controller 返回值处理]] · [[SpringMVC-HTTP请求处理全链路|返回索引]] · [[07-源码调试实战|下一篇：源码调试实战]]

## 1. 异常从哪里进入统一处理

`DispatcherServlet.doDispatch()` 会捕获：

- Handler 查找后的处理异常；
- 参数解析异常；
- 数据绑定与校验异常；
- Controller 业务异常；
- 返回值处理异常；
- 视图处理前的异常。

主流程：

```java
DispatcherServlet#doDispatch()
    try {
        // 查找Handler
        // 调用HandlerAdapter
        // 执行Controller
    }
    catch (Exception ex) {
        dispatchException = ex;
    }

    DispatcherServlet#processDispatchResult(
            request,
            response,
            handlerChain,
            modelAndView,
            dispatchException)

        DispatcherServlet#processHandlerException()                   // ★异常入口
```

## 2. `HandlerExceptionResolver`

`processHandlerException()` 按顺序遍历异常解析器：

```java
for (HandlerExceptionResolver resolver : handlerExceptionResolvers) {
    ModelAndView exMv =
            resolver.resolveException(
                    request, response, handler, ex);

    if (exMv != null) {
        return exMv;
    }
}
```

常见实现：

| 解析器 | 处理内容 |
| --- | --- |
| `ExceptionHandlerExceptionResolver` | `@ExceptionHandler`、`@ControllerAdvice` |
| `ResponseStatusExceptionResolver` | `@ResponseStatus`、`ResponseStatusException` |
| `DefaultHandlerExceptionResolver` | Spring MVC 内置异常 |

如果没有解析器能够处理，异常继续抛给 Servlet 容器。

## 3. `@ExceptionHandler` 调用链

```java
ExceptionHandlerExceptionResolver#resolveException()

    ExceptionHandlerExceptionResolver
        #doResolveHandlerMethodException()

        getExceptionHandlerMethod(handlerMethod, exception)
            // 先查Controller
            // 再查@ControllerAdvice

        ServletInvocableHandlerMethod#invokeAndHandle()
            // 调用@ExceptionHandler方法
            // 仍使用同一套参数解析器和返回值处理器
```

示例：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(OrderNotFoundException.class)
    public ResponseEntity<ProblemDetail> handle(
            OrderNotFoundException ex) {

        ProblemDetail detail =
                ProblemDetail.forStatus(HttpStatus.NOT_FOUND);
        detail.setDetail(ex.getMessage());

        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(detail);
    }
}
```

`@ExceptionHandler` 的返回值仍会经过：

```text
HandlerMethodReturnValueHandler
  -> HttpMessageConverter或ViewResolver
  -> HTTP响应
```

## 4. 常见异常与状态码

| 场景 | 异常 | 常见状态码 |
| --- | --- | --- |
| JSON 语法错误 | `HttpMessageNotReadableException` | 400 |
| `@Valid` 校验失败 | `MethodArgumentNotValidException` | 400 |
| 参数类型转换失败 | `MethodArgumentTypeMismatchException` | 400 |
| 缺少请求参数 | `MissingServletRequestParameterException` | 400 |
| 缺少请求头 | `MissingRequestHeaderException` | 400 |
| HTTP 方法不匹配 | `HttpRequestMethodNotSupportedException` | 405 |
| Content-Type 不支持 | `HttpMediaTypeNotSupportedException` | 415 |
| 无法满足 Accept | `HttpMediaTypeNotAcceptableException` | 406 |
| 没有 Handler | 404 处理流程 | 404 |

## 5. Controller 异常为什么能被识别？

普通 Java Controller 最终通过：

```java
Method#invoke(controllerBean, args)
```

调用。业务异常会先被反射包装成 `InvocationTargetException`。

`InvocableHandlerMethod.doInvoke()` 会拆包并重新抛出真实异常，所以异常解析器看到的是业务异常，而不是外层反射异常。

## 6. Filter 与 Interceptor 的位置

```text
客户端
  -> Filter
    -> DispatcherServlet
      -> Interceptor.preHandle
        -> Controller
      <- Interceptor.postHandle
      <- Interceptor.afterCompletion
    <- DispatcherServlet
  <- Filter
```

| 对比项 | Filter | HandlerInterceptor |
| --- | --- | --- |
| 所属体系 | Servlet | Spring MVC |
| 执行位置 | DispatcherServlet 外部 | HandlerAdapter 调用前后 |
| 是否知道 HandlerMethod | 通常不知道 | 知道 |
| 可否包装 request/response | 可以 | 通常不用于包装 |
| 常见用途 | 编码、安全、跨域、请求包装 | 权限、埋点、Controller 日志 |

## 7. 三个拦截器方法

假设注册 A、B：

```text
A.preHandle()
  -> B.preHandle()
    -> Controller
  <- B.postHandle()
<- A.postHandle()
  -> 响应处理或视图渲染
<- B.afterCompletion()
<- A.afterCompletion()
```

规律：

- `preHandle()`：正序；
- `postHandle()`：逆序；
- `afterCompletion()`：逆序；
- `postHandle()` 只在同步 Controller 正常完成后调用；
- `afterCompletion()` 用于最终资源清理。

### `preHandle()` 返回 `false`

```java
if (!interceptor.preHandle(request, response, handler)) {
    triggerAfterCompletion(...);
    return false;
}
```

结果：

- 后续拦截器不执行；
- Controller 不执行；
- 已成功执行 `preHandle()` 的拦截器逆序完成；
- 当前拦截器应自行设置响应。

## 8. REST 接口的 `postHandle()`

对于 `ResponseEntity` 或 `@ResponseBody`：

```text
Controller返回
  -> 响应体已经写入或正在写入
  -> ModelAndView为null
  -> postHandle(request, response, handler, null)
```

因此不能依赖 `postHandle()` 修改 REST 响应体。统一包装响应体更适合使用：

```text
ResponseBodyAdvice
```

## 9. 异步请求

如果 Controller 启动异步处理：

```text
doDispatch()
  -> HandlerAdapter.handle()
  -> WebAsyncManager.isConcurrentHandlingStarted() == true
  -> 当前Servlet线程提前返回
  -> applyAfterConcurrentHandlingStarted()
```

异步结果完成后会再次调度。此时：

- Filter 需要支持 ASYNC dispatcher；
- Interceptor 可以实现 `AsyncHandlerInterceptor`；
- 线程上下文不能假设自动保留；
- `postHandle()` 与 `afterCompletion()` 的时机不同于同步请求。

## 10. 异常处理的最终记忆链

```text
参数解析或Controller抛异常
  -> DispatcherServlet捕获
  -> processHandlerException()
  -> ExceptionHandlerExceptionResolver
     或ResponseStatusExceptionResolver
     或DefaultHandlerExceptionResolver
  -> 得到ModelAndView或直接写响应
  -> afterCompletion()
```
