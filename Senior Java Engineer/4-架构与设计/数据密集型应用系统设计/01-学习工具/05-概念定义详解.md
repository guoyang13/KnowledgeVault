# DDIA 概念定义详解

> 全书核心概念的**正式定义、机制、公式与边界**。章节精读中的「为什么」在这里找「是什么」。

## 可靠性

### Fault 与 Failure

| 术语 | 定义 |
|---|---|
| **Fault（故障）** | 系统组件偏离正常标准的状态，如磁盘坏道、进程 crash、错误配置。 |
| **Failure（失效）** | 系统作为整体**对用户停止提供服务**或返回错误结果。 |
| **Fault tolerance（容错）** | 在 fault 存在时仍避免 failure 的设计；通常靠**冗余 + 快速检测 + 自动恢复**。 |
| **MTTF** | Mean Time To Failure，平均无故障时间。 |
| **MTTR** | Mean Time To Repair，平均修复时间。 |
| **可用性** | 近似 `MTTF / (MTTF + MTTR)`；「几个 9」指年度 downtime 比例。 |

**关键区分**：单台机器 fault 不可避免；分布式目标是把 fault **限制在局部**，避免升级为全局 failure。

### 可靠性维度

| 类型 | 例子 | 设计手段 |
|---|---|---|
| 硬件 fault | 磁盘、电源、网络设备 | RAID、多副本、多 AZ |
| 软件 fault | Bug、内存泄漏、死锁 | 测试、隔离、熔断、回滚 |
| 人为 fault | 误删表、错误发布 | 权限、审计、备份、变更流程 |

## 性能指标

### 延迟 Latency

- **定义**：请求发出到收到响应的时间间隔。
- **百分位**：p50（中位数）、p95、p99、p999；**尾部延迟**决定「最慢那批用户」体验。
- **为什么不用平均值**：少数极慢请求会被平均掉；排队效应使 p99 对容量规划更关键。

### 吞吐量 Throughput

- **定义**：单位时间处理的记录数或请求数（records/s、QPS）。
- **与延迟关系**：负载接近饱和时，吞吐上升但延迟急剧恶化（排队论）。

### 负载参数 Load parameters

描述「负载是什么」的指标，例如：

- Web：requests/s、读写比、session 数
- 社交：发帖率、粉丝分布（幂律 → 热点）
- 搜索：索引大小、查询 QPS、写入 QPS

**设计必须先量化负载参数**，再谈扩展方案。

## 数据模型

### 关系模型 Relational

- **定义**：数据以**关系（表）**组织，通过**外键**表达引用；**规范化**减少冗余。
- **联结 Join**：在查询时组合多表；适合 **many-to-many**、复杂过滤与聚合。
- **Schema-on-write**：写入时强制结构。

### 文档模型 Document

- **定义**：记录常为自包含 JSON/BSON 文档；一对多常**嵌套**。
- **Schema-on-read**：结构由读方解释；灵活但应用层承担校验。
- **局限**：多对多、跨文档原子更新弱于关系库。

### 图模型 Graph

- **定义**：**顶点（实体）+ 边（关系）**；遍历多跳关系自然。
- **适用**：社交网络、权限继承、知识图谱、路径查询。
- **查询语言**：Cypher、Gremlin、SPARQL。

### 三者的本质权衡

| 维度 | 关系 | 文档 | 图 |
|---|---|---|---|
| 多对多 | 强 | 弱 | 强 |
| 嵌套 1:N | JOIN 或冗余 | 天然嵌套 | 边连接 |
| 模式灵活性 | 低 | 高 | 中 |
| 扩展模式 | 成熟 | 视产品 | 较窄 |

## 存储引擎

### WAL（Write-Ahead Log）

- **定义**：先追加写**顺序日志**，再更新数据结构；崩溃后通过重放 WAL 恢复。
- **作用**：将随机写转为顺序写；保证 **durability** 的基础。

### SSTable（Sorted String Table）

- **定义**：磁盘上**按键排序、不可变**的键值文件；合并（Compaction）产生新 SSTable。
- **读路径**：MemTable + 多层 SSTable（可能 Bloom filter 跳过）。

### LSM-Tree

- **定义**：Log-Structured Merge-Tree；写先入内存 MemTable，刷盘为 SSTable，后台 Compaction 合并。
- **写优化**：顺序写磁盘，高写入吞吐。
- **代价**：**读放大**（查多层）、**写放大**（Compaction 重写）、**空间放大**。
- **代表**：LevelDB、RocksDB、Cassandra、HBase。

### B-Tree / B+Tree

- **定义**：平衡树；按**固定大小页**（如 4KB）组织；更新时**原地或 COW** 修改页。
- **读优化**：范围查询、点查稳定；页分裂/合并维护平衡。
- **代表**：InnoDB（聚簇索引 = 主键 B+Tree）。

### OLTP vs OLAP

| | OLTP | OLAP |
|---|---|---|
| **定义** | 在线事务处理，短查询、少量行 | 在线分析，大扫描、聚合 |
| **存储** | 行存 Row-oriented | 列存 Column-oriented |
| **模式** | 规范化 | 星型/雪花维度模型 |
| **索引** | B+Tree 等 | 列压缩、向量化执行 |

## 编码演化

### 向后兼容 / 向前兼容

| 术语 | 定义 | 场景 |
|---|---|---|
| **向后兼容 Backward compatible** | **新代码**能读**旧数据** | 服务升级后读历史消息 |
| **向前兼容 Forward compatible** | **旧代码**能读**新数据** | 滚动升级期间老实例读新字段 |
| **Full compatibility** | 两者同时满足 | 理想的消息 Schema 策略 |

### Protobuf / Avro 演化规则（要点）

- 字段用 **编号 tag**，不用名字匹配。
- **添加字段**：新 tag，旧 reader 忽略 → 向后兼容读。
- **删除字段**：保留 tag 不用，或 reserved。
- **禁止**：改 tag 类型、复用已删 tag。

## 复制与读保证

### Leader-Based Replication

- **Leader**：唯一接受**写**；写入顺序写入复制日志。
- **Follower**：拉取或推送日志，按序重放。
- **同步复制**：Leader 等 Follower 确认；RPO 小，可用性降。
- **异步复制**：Leader 不等；**复制延迟 lag** 存在。

### Replication Lag 带来的异常

用户写 Leader 后立即读 Follower，可能读到旧数据。

### 四种客户端读保证（书中核心）

| 保证 | 定义 | 典型实现 |
|---|---|---|
| **读己之所写 Read your writes** | 用户总能读到自己刚写的内容 | 读 Leader；或 user_id 路由固定副本 |
| **单调读 Monotonic reads** | 同一用户不会先读新再读旧 | 固定路由到同一副本 |
| **一致前缀读 Consistent prefix** | 因果顺序不乱：若 B 依赖 A，则先看到 A | 按因果/version 路由；单分区有序 |
| **尾部一致** | 写入停止后，所有读者最终看到相同 | 最终一致 + 足够传播时间 |

### Multi-Leader

- **定义**：多个节点接受写；需**冲突解决**（LWW、版本向量、合并函数）。
- **场景**：多数据中心、离线协作。
- **风险**：冲突处理复杂、违背直觉的合并结果。

## Quorum

### 定义

**Leaderless replication**（Dynamo 风格）：N 个副本；写需 **W** 个确认，读需 **R** 个响应。

### 重叠条件

若 **W + R > N**，读写集合必有交集，理论上能读到最新写（在版本号比较正确的前提下）。

### 常见配置

- N=3, W=2, R=2：容忍 1 节点故障。
- **Sloppy quorum**：暂时写备用节点 + **hinted handoff** 回传。
- **Read repair**：读时发现版本旧则写回新值。
- **Anti-entropy**：后台 Merkle 树比对修复。

### Vector Clock（冲突检测）

- 多主或无主并发写时，用**版本向量**判断并发 vs 因果，供应用合并。

## 分区

### Partition / Shard

- **定义**：按 **partition key** 将数据拆到不同节点，每分区是键值子集。
- **目标**：水平扩展存储与吞吐。

### 分区策略

| 策略 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **Key Range** | 连续 key 区间 | 范围扫描 | 热点（最新时间戳） |
| **Hash** | hash(key) mod N | 负载均匀 | 丧失范围查询 |
| **复合键** | (tenant_id, record_id) | 租户内有序 | 设计复杂 |

### 次级索引与分区

- **Local（document）索引**：索引与主文档同分区；写快，全局查询需 scatter-gather。
- **Global（term）索引**：按索引值分区；全局查询快，写需跨分区。

### Rebalancing

节点增删时迁移分区；理想：**迁移量小、不影响在线请求、无需一次性全量**。

## 事务与隔离

### 事务 Transaction

- **定义**：将多个读写在逻辑上绑为一个单元：**全部成功提交或全部失败**。

### ACID 精确定义

| | 定义 | 注意 |
|---|---|---|
| **A Atomicity** | 失败时回滚已做修改 | undo log / WAL |
| **C Consistency** | 事务前后满足**应用不变量** | DB 只保证约束，不保证所有业务规则 |
| **I Isolation** | 并发事务效果等价于某种串行顺序 | 由隔离级别决定 |
| **D Durability** | 提交后不因 crash 丢失 | WAL + fsync + 复制 |

### 异常现象 Anomalies

| 异常 | 定义 | 哪级能防 |
|---|---|---|
| **脏读 Dirty read** | 读到未提交数据 | RC+ |
| **不可重复读 Non-repeatable read** | 同事务内两次读同一行结果不同 | SI/RR+ |
| **幻读 Phantom read** | 同事务内两次范围查询行数不同 | Serializable / RR+间隙锁 |
| **写偏斜 Write skew** | 两事务基于相同快照各写，破坏全局不变量 | Serializable 或显式锁 |
| **丢失更新 Lost update** | 两写覆盖 | 原子写 / 乐观锁 |

### 隔离级别对照（标准 SQL vs 实现）

| 级别 | 脏读 | 不可重复读 | 幻读 | 写偏斜 |
|---|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 | 可能 |
| Read Committed | 否 | 可能 | 可能 | 可能 |
| Snapshot Isolation | 否 | 否 | 视实现 | 可能 |
| Repeatable Read (InnoDB) | 否 | 否 | 多数防 | 可能 |
| Serializable | 否 | 否 | 否 | 否 |

### MVCC

- **定义**：Multi-Version Concurrency Control；每行多版本，读事务看**快照**，写创建新版本。
- **快照隔离 SI**：事务开始时取 consistent snapshot；**无幻读（部分）**但**有写偏斜**。

### 可串行化实现

| 方法 | 机制 |
|---|---|
| 实际串行 | 单线程执行事务 |
| 2PL | 两阶段锁，读写锁 |
| SSI | Serializable Snapshot Isolation，检测 rw-conflict 并 abort |

## 分布式故障

### 部分失效 Partial failure

- **定义**：分布式系统中，**不确定**某请求是慢还是失败；**没有全局共享内存**。
- **推论**：不能依赖「要么成功要么异常」的单机语义。

### 超时 Timeout

- **定义**：等待超过阈值则放弃；但**无法区分**网络慢、进程暂停、节点宕机。
- **风险**：重复请求 → 需**幂等**。

### 时钟

| 类型 | 用途 | 陷阱 |
|---|---|---|
| Time-of-day | 人类时间 | NTP 跳变，不可做顺序 |
| Monotonic | 测间隔 | 不能跨节点比较 |

### Fencing Token

- **定义**：单调递增的**租约编号**；存储拒绝旧 token 的写，防止**过期 leader** 破坏数据。

## 一致性级别

### 线性一致性 Linearizability

- **定义**：所有操作看起来在**单个副本**上按**实时**顺序发生；读必返回**最新写**的结果。
- **代价**：延迟、可用性（CAP 分区时）。
- **用途**：锁、唯一性、协调服务。

### 顺序一致性 vs 因果一致性

| | 定义 |
|---|---|
| **顺序一致** | 所有节点看到相同的全局顺序（不必实时） |
| **因果一致** | 仅保证有因果关系的操作顺序 |

### 共识 Consensus

- **定义**：多个节点对**单个值**（如 leader、序列号）达成一致。
- **FLP**：异步确定性共识在允许一个节点崩溃时**不可能**（理论下界）。
- **Raft**：选主 + 日志复制 + 过半提交；易理解。

## 分布式事务

### 2PC Two-Phase Commit

1. **Prepare**：协调者问参与者能否提交；参与者写 prepare log 并投票。
2. **Commit/Abort**：协调者根据投票决定；参与者执行。

- **阻塞**：协调者挂掉时参与者可能**阻塞等待**。
- **XA**：2PC 的工业接口标准。

### Saga

- **定义**：长事务拆为**本地事务链** + **补偿事务**；无全局锁。
- **语义**：最终一致；补偿可能**无法完全撤销**（需业务设计）。

## 批处理

### MapReduce

1. **Map**：输入分片，输出 (key, value) 对。
2. **Shuffle**：按 key 分区、排序、传送到 Reduce 节点。
3. **Reduce**：同 key 聚合。

- **局限**：Shuffle 磁盘 IO 重；迭代、交互查询不友好。

### Dataflow Engine

- Spark、Flink 等：内存 DAG、**迭代**、**增量**；比经典 MR 快一个数量级。

## 流处理

### 日志 vs 队列

| | 消息队列 | 日志（Kafka） |
|---|---|---|
| 消费 | 通常删除或 ack | **保留**，可重放 |
| 消费者 | 竞争消费 | **独立 consumer group** |
| 用途 | 任务分发 | **数据集成** |

### CDC

- **定义**：Change Data Capture；读取 DB **事务日志**（binlog/WAL）获取变更流。
- **作用**：单写 DB，**衍生视图**异步更新，避免双写。

### 事件溯源 Event Sourcing

- **定义**：应用状态由**不可变事件序列**推导；当前状态 = fold(events)。
- **优点**：审计、重放、多视图；**缺点**：查询需物化、Schema 演化复杂。

### 交付语义

| 语义 | 含义 |
|---|---|
| At-most-once | 可能丢，不重复 |
| At-least-once | 可能重复，不丢（+ 幂等） |
| Exactly-once | 端到端恰好一次（难，常近似） |

## 数据集成

### System of Record

- **定义**：某一数据的**权威真相源**；其他副本均为 **derived data（衍生数据）**。

### Unbundling the Database

- **定义**：把传统 RDBMS 的能力拆开：事务存储、全文索引、缓存、复制、分析——各用**专用引擎**，用 **CDC/日志** 集成。

### 物化视图 Materialized View

- **定义**：预计算查询结果并存储；源数据变时需**增量更新**或重算。

---

## 与 CAP 的关系（书中观点）

- **CAP**：Consistency、Availability、Partition tolerance 三者不可兼得（在**网络分区**发生时）。
- **书中强调**：CAP 过于粗糙；工程上应讨论**具体一致性模型**、**延迟**、**运维成本**，而非贴标签。

## 核心概念辨析

这部分专门处理“看起来相似，实际边界不同”的概念。设计评审里很多争论，本质是这些边界没说清。

### Fault vs Failure

| 概念 | 含义 | 设计动作 |
|---|---|---|
| Fault | 某个组件、请求、节点、磁盘、网络出现异常 | 检测、隔离、重试、降级 |
| Failure | 系统没有向用户提供承诺的服务 | SLA、错误预算、用户可见影响 |

可靠性设计不是消灭所有 fault，而是阻止 fault 扩散成用户可见 failure。

### Replication vs Partitioning

| 概念 | 解决什么 | 带来什么新问题 |
|---|---|---|
| 复制 | 可用性、读扩展、容灾、地理就近 | 复制延迟、冲突、读保证 |
| 分区 | 容量、写扩展、数据规模 | 路由、热点、跨分区操作、再平衡 |

复制让同一份数据有多个副本；分区让不同数据落到不同节点。实际系统通常两者同时使用。

### Consistency vs Isolation vs Consensus

| 概念 | 所属问题 | 例子 |
|---|---|---|
| Consistency model | 副本或对象对外呈现什么可见性 | 最终一致、线性一致 |
| Isolation level | 并发事务之间互相看到什么 | RC、RR、SI、Serializable |
| Consensus | 节点如何对某个决定达成一致 | Raft、Paxos、Zab |

不要把“一致性”一词混用。评审时要明确讨论的是副本读语义、事务隔离，还是节点决策。

### Linearizability vs Serializability

| 概念 | 关注点 | 判断方式 |
|---|---|---|
| Linearizability | 单个对象或操作看起来像实时生效 | 操作完成后，后续读必须看到它 |
| Serializability | 多个事务的执行结果像某个串行顺序 | 不要求符合真实时间顺序 |

线性一致强调“实时可见”；可串行化强调“事务结果正确”。两者可以组合，但不是同一个保证。

### 2PC vs Saga vs Outbox

| 方案 | 保证 | 优点 | 代价 |
|---|---|---|---|
| 2PC/XA | 跨资源原子提交 | 语义强 | 阻塞、慢、运维复杂 |
| Saga | 长流程最终一致 | 可用性高，适合业务补偿 | 补偿逻辑复杂，中间状态可见 |
| Outbox | 本地事务 + 可靠事件发布 | 避免业务库和 MQ 双写 | 需要投递器、幂等、重放 |

默认思路：能本地事务就本地事务；不能时优先 Outbox/Saga；强一致跨资源是最后手段。

### Queue vs Log

| 概念 | 语义 | 典型场景 |
|---|---|---|
| Queue | 消息被消费者组分摊处理，处理后通常不再关心 | 任务分发、异步执行 |
| Log | 消息按顺序追加并保留，消费者按 offset 读取 | 事件流、CDC、重放、衍生视图 |

Kafka 更接近日志；传统 MQ 更接近队列。用 Kafka 做事件总线时，要利用它的保留和重放能力，而不只是“发消息”。

### System of Record vs Derived Data

| 概念 | 含义 | 设计问题 |
|---|---|---|
| System of Record | 权威数据源 | 谁有写权限，如何保护不变量 |
| Derived Data | 从真相源派生的数据 | 如何同步、重建、修复、对账 |

缓存、搜索索引、报表库、推荐特征多数是衍生数据。衍生数据不怕删了重建，怕不知道从哪里重建。

### Exactly-once 的现实含义

“Exactly-once”通常不是说外部世界绝不重复，而是说在特定系统边界内，输入 offset 和输出结果能以事务方式提交，重复执行不会造成重复效果。

落地时要同时看：

- 消费者是否幂等。
- 输出存储是否有唯一键或版本。
- offset 与结果是否原子提交。
- 失败后能否重放。
- 下游副作用是否可去重。
