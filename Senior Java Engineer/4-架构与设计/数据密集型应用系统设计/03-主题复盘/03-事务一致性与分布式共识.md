# 事务、一致性与分布式共识

> Part II 后半横向复盘（第 7–9 章）。**设计分布式业务前必读**：本地事务边界、跨服务一致性、读保证与共识的选型。

## 本复盘要解决的三个问题

1. **单库内**：用什么隔离级别？防哪些异常？
2. **跨服务**：要不要分布式事务？用什么模式？
3. **跨副本**：读路径需要什么一致性与读保证？

定义详见 [[05-概念定义详解#事务与隔离]]、[[05-概念定义详解#一致性级别]]、[[05-概念定义详解#分布式事务]]。

## 一、单库事务与隔离级别

### 异常现象速查

| 异常 | 定义 | 典型业务后果 |
|---|---|---|
| 脏读 | 读到未提交 | 基于脏数据决策 |
| 不可重复读 | 同事务内重读变 | 报表中途变 |
| 幻读 | 范围行数变 | 批量操作漏行 |
| **写偏斜** | 全局不变量破坏 | 库存/排班错误 |
| 丢失更新 | 写覆盖 | 计数错误 |

### 隔离级别选型表

| 业务场景 | 推荐级别 | 补充手段 |
|---|---|---|
| 普通 CRUD | RC 或 RR | 乐观锁 version |
| 账户余额 | RR + `FOR UPDATE` 或 Serializable | 单行热点 |
| 库存（单行） | RR + 原子 `UPDATE qty=qty-1 WHERE qty>=1` | — |
| 库存（多行不变量） | Serializable 或物化计数行 | 防写偏斜 |
| 只读报表 | RC + 只读从库快照 | 短事务 |
| 后台批处理 | RC | 避免长 RR |

### 写偏斜解法对照

| 方法 | 机制 | 适用 |
|---|---|---|
| Serializable / SSI | DB 检测冲突 abort | PostgreSQL |
| 显式范围锁 | `SELECT ... FOR UPDATE` 锁所有相关行 | InnoDB |
| 物化冲突 | 单行 `ON_CALL_COUNT` 更新 | 排班、配额 |
| 串行队列 | 单线程处理冲突资源 | 高性能计数 |

## 二、分布式一致性方案全对比

| 方案 | 一致性 | 可用性 | 性能 | 复杂度 | 典型场景 |
|---|---|---|---|---|---|
| **本地事务** | 强（单库） | 高 | 高 | 低 | 单服务单库聚合 |
| **2PC / XA** | 强 | 低（阻塞） | 低 | 高 | 遗留异构集成，慎用 |
| **3PC** | 强 | 中 | 低 | 很高 | 理论多，生产少 |
| **Seata AT** | 较强 | 中 | 中 | 中 | Java 微服务同构 |
| **Seata TCC** | 可调 | 中 | 中 | 高 | 预留/确认/取消 |
| **Saga** | 最终 | 高 | 高 | 中 | 长流程订单 |
| **Outbox** | 最终 | 高 | 高 | 中 | **默认推荐** |
| **事务消息** | 最终 | 高 | 高 | 中 | RocketMQ 半消息 |
| **CDC + 对账** | 最终 | 高 | 高 | 中 | 衍生视图同步 |

### 决策树（设计文档可直接粘贴）

```text
Step 1: 能否在一个限界上下文内、一个聚合、一次本地事务完成？
  ├─ 是 → 本地 ACID（首选，见 DDD 聚合边界）
  └─ 否 → Step 2

Step 2: 跨服务操作是否必须「用户立即可感知」的强一致？
  ├─ 是 → TCC / 可串行化资源（库存预留、座位锁定）
  │        慎用 2PC/XA（阻塞、运维难）
  └─ 否 → Step 3

Step 3: 能否接受秒级~分钟级最终一致 + 对账？
  ├─ 是 → Outbox / Saga / 事务消息 + 幂等 + 补偿
  └─ 否 → 重新审视聚合划分（可能边界划错）
```

### Outbox 模式（推荐默认）

```text
BEGIN TRANSACTION
  INSERT INTO orders ...
  INSERT INTO outbox (event_type, payload, ...) ...
COMMIT

── 独立 Poller / Debezium ──► MQ ──► 下游消费者（幂等）
```

**优点**：与业务**同库同事务**；避免 2PC；与 CDC 天然契合。

## 三、一致性与读保证（跨副本）

### 一致性模型光谱

```text
最终一致 ──► 因果一致 ──► 顺序一致 ──► 线性一致
  便宜                                      昂贵
```

| 模型 | 定义 | 何时需要 |
|---|---|---|
| 最终一致 | 停止写后最终相同 | 缓存、搜索索引 |
| 因果一致 | 因果相关操作有序 | 社交评论链 |
| 线性一致 | 实时全局序 | 锁、选主、唯一约束 |

### 四种客户端读保证（第 5 章）

| 保证 | 定义 | 实现要点 |
|---|---|---|
| Read your writes | 读到自己刚写的 | 写后读主；user 路由固定副本 |
| Monotonic reads | 不先新后旧 | 同用户固定 replica |
| Consistent prefix | 因果序 | 版本向量；单分区有序 |
| Eventual | 最终相同 | 接受 lag，监控 lag |

**设计动作**：为每个读 API 标注上表中的一行或多行。

## 四、共识与协调

| 机制 | 用途 | 实现 |
|---|---|---|
| **Raft** | Leader 选举、日志复制 | etcd, Consul |
| **Fencing token** | 防过期 leader 写 | 存储校验 epoch |
| **Total order broadcast** | 全局有序消息 | Kafka 单分区 / Raft 日志 |

### 2PC 两阶段（知悉即可）

1. **Prepare**：参与者投票，写 prepare log  
2. **Commit/Abort**：协调者决定  

**问题**：协调者宕机 → 参与者阻塞；性能差。**替代**：Saga、Outbox。

## 五、Java 栈落地对照

| 需求 | 推荐 |
|---|---|
| 单服务事务 | `@Transactional` + InnoDB |
| 跨服务最终一致 | Outbox + RocketMQ/Kafka |
| 库存预留 | TCC 或 Redis Lua + 对账 |
| 读己之所写 | 写后 `@DS("master")` 或 ThreadLocal 路由 |
| 分布式锁 | Redisson + **业务版本校验**（非仅锁） |
| 幂等 | 唯一索引 + Idempotency-Key |

## 七、常见误区

| 误区 | 正解 |
|---|---|
| 分布式事务 = 2PC | 优先本地事务 + 事件 |
| RR = 无并发 bug | 仍有写偏斜 |
| 加 Seata 就万事大吉 | 仍有性能、脏写、运维成本 |
| 最终一致 = 不用设计 | 必须定义 lag、顺序、补偿 |
