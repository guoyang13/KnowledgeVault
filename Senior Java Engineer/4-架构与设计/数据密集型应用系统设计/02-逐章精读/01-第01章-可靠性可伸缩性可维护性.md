# 第 01 章：可靠性、可伸缩性、可维护性

> 本章目标：建立评价数据系统的**三维框架**，后续所有技术选型都回到这三个词做权衡。

## 本章在全书中的位置

全书「元章节」。不教具体工具，而是定义**好系统长什么样**，以及架构师应问哪些问题。

## 初学者先抓住一句话

**数据密集型应用**的主要挑战是数据（量、复杂度、变化速度）；设计目标是在 **可靠性、可伸缩性、可维护性** 之间做可接受的权衡。

## 关于数据系统的思考

现代应用很少「一个数据库打天下」，典型组合：

```text
应用服务器
  ├── 主数据库（OLTP）
  ├── 缓存（Redis）
  ├── 搜索索引（Elasticsearch）
  ├── 消息队列（Kafka / RocketMQ）
  └── 分析/数仓（离线）
```

架构师任务：**为每个工作负载选对工具**，并理解组合后的故障模式与一致性问题。

## 可靠性 Reliability

**定义**：故障（fault）发生时，系统仍能**正确工作**（用户感知为 failure 的概率低）。

### 故障类型

| 类型 | 例子 | 应对思路 |
|---|---|---|
| 硬件 | 磁盘坏、电源、网络卡 | 冗余、RAID、多 AZ |
| 软件 | Bug、级联失败、资源泄漏 | 测试、隔离、限流、快速回滚 |
| 人为 | 误删数据、错误配置 | 权限、审计、备份、演练 |

### 设计原则

- **容错 ≠ 零故障**：目标是 fault-tolerant，不是 fault-free。
- **快速恢复** 往往比 **预防一切** 更现实。
- **混沌工程**：主动注入故障验证假设。

## 可伸缩性 Scalability

**定义**：负载增长时，系统能以**可接受的方式**增加资源应对。

### 描述负载

用 **负载参数** 而非 vague「大流量」：

- Web：并发请求、读写比
- 社交：粉丝数、发帖频率
- 搜索：索引大小、查询 QPS

### 描述性能

| 指标 | 适用 |
|---|---|
| 吞吐量 | 批处理、后台任务 |
| 响应时间中位数 | 典型体验 |
| **p95 / p99 延迟** | 尾部体验、SLA |
| 资源利用率 | 成本与容量规划 |

> **关键洞见**：平均值会骗人；扩容后 p99 可能因排队、共享资源反而变差。

### 扩展方式

| 方式 | 说明 |
|---|---|
| 垂直扩展 | 更强单机，简单但有上限 |
| 无共享架构 | 多节点 + 分区，DDIA 后续重点 |

**避免过早优化**：小团队不必第一天就分片；但**数据结构、无状态应用、清晰边界**应早做，便于日后扩展。

## 可维护性 Maintainability

三要素：

| 维度 | 含义 | 实践 |
|---|---|---|
| **可操作性** | 运维能否看懂、排障 | 监控、日志、追踪、文档 |
| **简单性** | 复杂度可控 | 避免过度抽象、清晰模块边界 |
| **可演化性** | 需求变化时易改 | 松耦合、Schema 演化、自动化测试 |

## 架构设计检查清单（本章）

评审任何模块前自问：

1. **可靠性**：单点在哪？备份与恢复策略？人为误操作如何防？
2. **可伸缩性**：预期 10x 流量时，先瓶颈的是 CPU、磁盘、网络还是单 Key？
3. **可维护性**：新人能否在 1 周内改一条核心链路？变更是否需动多处？

## 与 Java 后端的关系

- Spring Boot 微服务：**无状态应用层** + **有状态数据层**，扩展性常从数据层开始。
- JVM **GC 停顿** 是 p99 延迟的常见来源（联系第 8 章时钟与停顿）。
- **可观测性**：Micrometer + Prometheus + 链路追踪，支撑可操作性。

## 本章小结（书中要点）

- 数据系统由多种组件组成，故障模式是组合式的。
- 用负载参数和百分位延迟**量化**扩展需求。
- 可维护性长期决定项目生死，不亚于性能。
