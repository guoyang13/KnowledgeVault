# 第 02 章：数据模型与查询语言

> 本章目标：理解**数据模型是思维工具**，选型取决于实体关系与访问模式，而非「新一定比旧好」。

## 初学者先抓住一句话

**关系模型**擅长多对多、联结查询；**文档模型**擅长一对多嵌套、局部读取；**图模型**擅长多对多关系遍历——没有银弹。

## 关系模型 vs 文档模型

### 关系模型（SQL）

- 数据规范化，减少重复。
- **联结（JOIN）** 表达多对多。
- Schema 强，适合结构稳定、一致性要求高。

### 文档模型（MongoDB 等）

- 一对多常 **嵌套** 在一个文档内（类似 JSON）。
- **多对多** 弱于关系库，常需应用层模拟或 `$lookup`。
- Schema 灵活：schema-on-read。

### 选型对照

| 场景 | 倾向 |
|---|---|
| 多表联结、复杂报表 | 关系型 |
| _catalog 树形、CMS、用户配置 | 文档型 |
| 订单头+行（常一起读） | 文档嵌套 或 关系+JOIN 均可 |
| 订单跨用户/商品多维度查询 | 关系型 |

## 数据查询语言

| 类型 | 例子 | 特点 |
|---|---|---|
| **声明式** | SQL | 描述「要什么」，优化器选执行计划 |
| **命令式** | 应用代码循环 | 灵活但易错、难优化 |
| **MapReduce 风格** | 早期 Mongo | 表达力强但冗长 |

> **设计启示**：把复杂聚合尽量放在**数据库能优化**的层（SQL、ES DSL），而非拉全量到应用内存。

## 图数据模型

- **顶点 + 边** 表达关系网络。
- 适合：社交关系、权限继承、知识图谱、欺诈环检测。
- 查询语言：Cypher、Gremlin、SPARQL。
- 与关系库对比：多跳关系遍历更自然；海量简单 CRUD 未必划算。

## 设计决策框架

```text
1. 实体间主要是 1:N、N:M 还是深图遍历？
2. 读模式：点查、范围、聚合、全文？
3. 写模式：整文档替换 vs 单行更新？
4. 是否需要强 Schema 与 DB 级约束（外键、唯一）？
5. 团队熟悉度与生态（事务、迁移、运维）
```

## 架构设计检查清单

- [ ] 是否因「NoSQL 快」而选文档库，却大量需要 JOIN？
- [ ] 嵌套文档是否无限增长（评论、日志）导致文档过大？
- [ ] 同一业务概念是否在多个服务各存一份不同结构？
- [ ] 查询语言是否把业务规则散落在 10 个微服务里？

## 与 Java 后端

- **MyBatis / JPA**：关系模型为主；注意 N+1 与过度 ORM 对象图。
- **MongoDB Template**：适合配置、日志型文档；跨文档事务需评估版本。
- **多模型并存**：OLTP 用 MySQL，搜索用 ES——见第 12 章「分拆数据库」。

## 本章小结

- 模型影响代码结构、查询方式、扩展路径。
- 文档与关系之争，本质是 **访问模式与规范化** 的权衡。
- 图模型是专用武器，不是默认选项。
