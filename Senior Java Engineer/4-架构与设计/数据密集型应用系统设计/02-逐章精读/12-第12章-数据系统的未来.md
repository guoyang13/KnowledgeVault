# 第 12 章：数据系统的未来

> 本章目标：把全书收束为 **「分拆数据库 + 数据集成 + 正确性」** 的架构观，指导微服务与数据中台设计。

## 初学者先抓住一句话

**没有一个系统适合所有工作负载**；用 **组合专用存储 + 统一数据流** 替代单一万能数据库。

## 数据集成

问题：同一份数据在 DB、缓存、搜索、数仓各一份，如何 **一致地** 同步？

| 反模式 | 正路 |
|---|---|
| 应用双写 DB + ES | CDC 或 Outbox 单写源 |
| 点对点 ETL 蜘蛛网 | **日志** 作为中心总线 |
| 隐式 Schema | Schema Registry + 契约测试 |

**衍生数据**：在线库是 **真相源（System of Record）**；其余是 **物化视图**。

## 分拆数据库 Unbundling the Database

传统 RDBMS = 存储 + 索引 + 缓存 + 复制 + 查询优化器。

现代栈 **拆开买**：

```text
PostgreSQL（事务源）
  → CDC → Kafka
    → Flink（流计算）
    → Elasticsearch（搜索）
    → Redis（热缓存）
    → S3 + Iceberg（湖仓）
```

**代价**：运维复杂度、一致语义、调试链路变长。

## 将事情做正确（Correctness）

- **端到端论证**：从用户操作到所有衍生视图的可验证性。
- **可审计、可重放**：日志保留、版本化 Schema。
- **测试**：确定性仿真、属性测试、回放生产流量（脱敏）。

## 做正确的事情（Ethics）

- 数据 retention、隐私、算法偏见、监控滥用。
- 架构师对 **数据用途** 负有责任，不仅是 uptime。

## 架构设计检查清单

- [ ] 每个微服务是否 **拥有自己的数据**，禁止跨库 JOIN？
- [ ] 跨服务查询是否通过 API / 物化读模型而非共享表？
- [ ] 是否有 **单一真相源** 与明确的衍生链路图？
- [ ] 新存储引入是否解决单一痛点，而非重复造轮子？

## 与 Java 后端 / DDD

- **限界上下文** 内：一个聚合 → 一个事务边界 → 常对应一个 schema。
- **上下文集成**：领域事件 + MQ，而非共享数据库（[[实现领域驱动设计]] 第 13 章）。
- **CQRS**：写模型在 OLTP，读模型由 CDC/事件构建。
- 供应链案例：[[00-新采购服务替换方案总览]] 中的双轨、Outbox 与 DDIA 高度一致。

## 本章小结

- 未来是 **专用组件 + 集成管道**，不是更大的一体机 DB。
- 正确性来自 **可验证的数据流**，不是口头「最终一致」。
- 与 DDD、微服务、数据中台在同一套叙事下对齐。
