# 第 06 章：分区

> 本章目标：理解如何把数据拆到多节点以**水平扩展**，以及分区键、再平衡、路由的设计陷阱。

## 初学者先抓住一句话

**分区（Sharding）** 解决单机容量与吞吐上限；选错分区键会导致热点与跨分区事务地狱。

## 分区与复制

每个分区通常有 **多个副本**（第 5 章），形成：

```text
Node A: [Partition 0 leader, Partition 1 follower]
Node B: [Partition 1 leader, Partition 0 follower]
```

## 键值数据的分区策略

| 策略 | 优点 | 缺点 |
|---|---|---|
| **Range** | 范围扫描方便 | 热点（最新时间戳） |
| **Hash** | 负载较均匀 | 丧失范围查询，需二级索引 |
| **复合键** | `(tenant_id, order_id)` 租户内有序 | 设计复杂 |

### 热点 Key

- celebrity 用户、促销商品。
- 缓解：**随机后缀**、**拆分计数器**、**异步聚合**。

## 分区与次级索引

全局二级索引在分区系统上很难：

| 方案 | 说明 |
|---|---|
| **Term partitioned** | 索引项按索引值分区 |
| **Document partitioned** | 索引随主文档分区（本地索引） |

→ 跨分区查询需 **Scatter-Gather**，延迟与成本高。

## 分区再平衡 Rebalancing

| 策略 | 说明 |
|---|---|
| Fixed number of partitions | 分区数固定，节点变只迁分区 |
| Dynamic partitioning | 分裂大分区 |
| Proportional to nodes | 一致性哈希等 |

**目标**：迁移量小、不影响请求、无需全量 reshuffle。

## 请求路由

客户端如何知道 Key → 节点？

- 任意节点转发（Redis Cluster、gossip）
- 路由层（Proxy）
- 客户端感知分区（Kafka client）

## 架构设计检查清单

- [ ] 分区键是否包含 **高基数** 且与访问模式一致？
- [ ] 是否需要跨分区事务？能否用 Saga / 按实体聚合？
- [ ] 扩容时再平衡是否自动化？是否演练？
- [ ] 二级索引查询是否意外变成全集群扫描？

## 与 Java 后端

- **分库分表**：ShardingSphere 按 `user_id` / `order_id`；避免按时间单表热点。
- **Kafka**：分区数决定并行度；Key 决定有序性边界。
- **Elasticsearch**：分片 + 副本；reindex 再平衡成本高，规划前置。

## 本章小结

- 分区是扩展的必经之路，但增加运维与查询复杂度。
- 分区键设计 = 数据局部性 + 负载均衡。
- 与复制结合才能既扩展又容错。
