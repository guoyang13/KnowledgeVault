# 第 05 章：复制

> 本章目标：理解复制如何提升**可用性与读扩展**，以及**复制延迟**带来的各种一致性问题与解法。

## 初学者先抓住一句话

**主从复制**让读扩展变简单，但异步 lag 会让用户看到「刚提交的数据不见了」——必须按业务定义读保证。

## 领导者与追随者（Leader-Follower）

```text
写请求 → Leader → 复制日志 → Follower(s)
读请求 → Follower 或 Leader
```

| 复制方式 | 特点 |
|---|---|
| 异步 | Leader 不等 Follower，lag 存在 |
| 同步 | 至少 N 个 Follower 确认才返回，可用性下降 |
| 半同步 | 折中（MySQL 半同步插件） |

**故障切换**：Follower 升 Leader 需 **共识**（谁是最新数据）→ 第 9 章。

## 复制延迟问题（极其重要）

| 保证 | 含义 | 典型实现 |
|---|---|---|
| **读己之所写** | 用户读自己的更新 | 读 Leader；或 user_id 路由同一副本 |
| **单调读** | 不会先新后旧 | 同用户固定读同一副本 |
| **一致前缀读** | 因果顺序不乱 | 按因果/version 路由 |
| **尾部一致** | 最终所有人看到相同 | 最终一致 + 足够时间 |

> **设计文档必写**：每个读 API 需要上表哪几级保证。

## 多主复制 Multi-Leader

- 多数据中心、多写节点。
- **冲突不可避免**：LWW、版本向量、应用层合并。
- 适合：离线协作、多活写入；不适合：强一致计数器。

## 无主复制 Leaderless（Dynamo 风格）

- 写 **Quorum**：W 个副本确认；读 **R** 个副本，R+W>N 可重叠。
- **Sloppy quorum + hinted handoff**：临时写备用节点。
- **Read repair / Anti-entropy**：后台修复不一致。
- 代表：Cassandra、DynamoDB、Riak。

## 架构设计检查清单

- [ ] 读写分离是否未处理 lag？用户投诉「数据丢了」？
- [ ] 缓存与 DB 双写顺序是否导致脏读？
- [ ] 主从切换 RPO/RTO 是否演练过？
- [ ] 从库是否承担报表导致 lag 拉大？

## 与 Java 后端

- **MySQL 读写分离**：ShardingSphere、MyCat；写后读需 **同库** 或 **延迟读主**。
- **Redis 主从 + 哨兵**：读从可能旧；金融类计数用 `READONLY` 谨慎。
- **Canal 订阅 binlog**：从 Leader 日志派生索引/缓存，避免双写。

## 本章小结

- 复制是可用性与读扩展的基础，lag 是默认代价。
- 多主与无主适合特定场景，冲突处理是核心复杂度。
- 读保证应产品化，而非假设「从库差不多就行」。
