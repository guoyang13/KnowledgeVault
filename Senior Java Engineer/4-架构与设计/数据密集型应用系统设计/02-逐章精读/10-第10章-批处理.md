# 第 10 章：批处理

> 本章目标：理解**大规模离线计算**的思路，以及 MapReduce 与 modern dataflow 的演进。

## 初学者先抓住一句话

**批处理**处理有界数据集，追求**高吞吐**而非毫秒延迟；输出常是 **衍生数据**（报表、索引、特征）。

## Unix 工具链的启示

```bash
sort | uniq -c | sort -nr | head
```

- **stdin/stdout** 组合、不可变文件、重新运行。
- 与 MapReduce：**分而治之 + 管道**。

## MapReduce 与分布式文件系统

```text
Input → Map（分片并行）→ Shuffle（按 key 分组）
     → Reduce（聚合）→ Output
```

| 优点 | 局限 |
|---|---|
| 容错（重试 map/reduce） | Shuffle 磁盘 IO 重 |
| 简单编程模型 | 迭代/交互查询不友好 |
| 与 HDFS 结合 | 延迟高（分钟级） |

## MapReduce 之后

| 引擎 | 改进 |
|---|---|
| **Spark** | 内存 DAG、迭代、比 MR 快一个数量级 |
| **FlumeJava / Tez** | 优化 MR 工作流 |
| **Materialized views** | 预聚合加速查询 |

**设计模式**：**Lambda** 批层修正速度层的近似结果。

## 架构设计检查清单

- [ ] 是否在 OLTP 库直接跑全表扫描报表？
- [ ] 批任务是否幂等、可重跑（分区 overwrite）？
- [ ] 输出是否写回在线库拖垮业务？
- [ ] 数据血缘是否可追溯（哪批 job 产出哪张表）？

## 与 Java 后端

- **Spark Java API / Scala**：离线 ETL、特征工程。
- **Spring Batch**：企业内中小批量；chunk  oriented。
- **数仓同步**：ODS → DWD → DWS，T+1 与业务库隔离。
- **与第 11 章**：批处理补历史，流处理补实时 → Lambda。

## 本章小结

- 批处理是衍生数据的主渠道之一。
- MR 思想仍有效，工程上多用 Spark 等 dataflow。
- 批与在线系统应 **物理隔离**。
