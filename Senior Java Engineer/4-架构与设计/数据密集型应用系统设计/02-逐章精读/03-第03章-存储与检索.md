# 第 03 章：存储与检索

> 本章目标：理解数据库**内部**如何用索引与日志组织数据，以便做出索引、分库、选型决策。

## 初学者先抓住一句话

**OLTP** 优化点查与短事务；**OLAP** 优化大规模扫描聚合——引擎结构完全不同。

## 驱动数据库的数据结构

### 哈希索引

- 内存 HashMap + 追加日志（WAL）。
- 点查快；**不支持范围查询**。
- 代表思路：Bitcask（Riak）。

### SSTable 与 LSM-Tree

```text
写入 → MemTable（内存）→ 刷盘 SSTable（有序不可变文件）
读取 → MemTable + 多层 SSTable 合并查找
后台 → Compaction 合并 SSTable
```

- **写放大**、**读放大**、**空间放大** 三权衡。
- 代表：LevelDB、RocksDB、Cassandra、HBase。

### B-Tree（B+Tree）

- 页为单位原地更新（或 COW）。
- **读优化**，范围查询友好。
- 代表：InnoDB、PostgreSQL。

| 维度 | LSM | B+Tree |
|---|---|---|
| 写吞吐 | 高（顺序写） | 中（随机写） |
| 读延迟 | 需合并多层 | 稳定 |
| 范围扫描 | 支持 | 优秀 |
| 典型 | 写多、时序 | 通用 OLTP |

## 事务处理 vs 分析（OLTP vs OLAP）

| | OLTP | OLAP |
|---|---|---|
| 访问 | 少量行，索引点查 | 大量行，聚合 |
| 存储 | 行存 | 列存 |
| 模式 | 规范化 | 星型/雪花维度模型 |
| 系统 | MySQL、PostgreSQL | ClickHouse、Redshift |

**HTAP**（混合）是趋势，但需理解并非免费午餐。

## 列存储

- 同列数据相邻 → **高压缩比**。
- 向量化执行、只读需要的列。
- 适合：BI 报表、用户行为分析。

## 设计启示

1. **索引不是免费的**：每次索引增加写开销与存储。
2. **主键 / 分区键** 决定数据物理局部性（联系第 6 章）。
3. **慢查询** 先查执行计划，是否全表扫描、是否索引失效。
4. **冷热分离**：热数据 SSD + 温冷对象存储。

## 架构设计检查清单

- [ ] 表是否缺少覆盖高频查询的复合索引？
- [ ] 是否在 OLTP 库跑大报表拖垮业务？
- [ ] 写入是否触发过多二级索引更新？
- [ ] 是否了解所用 DB 是 LSM 还是 B+Tree 语义？

## 与 Java 后端

- **InnoDB**：聚簇索引 = 主键 B+Tree；二级索引叶子存主键。
- **MyBatis 大分页**：`LIMIT offset` 深分页慢 → 游标/Seek 分页。
- **ES**：倒排索引 +  doc values，适合搜索与聚合，非事务源。

## 本章小结

- 存储引擎决定读写曲线；选型看访问模式。
- OLTP/OLAP 分离是成熟架构常见模式。
- 理解 WAL、Compaction 有助于理解复制与恢复（第 5 章）。
