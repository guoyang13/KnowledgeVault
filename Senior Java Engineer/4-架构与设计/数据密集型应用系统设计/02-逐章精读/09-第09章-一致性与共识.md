# 第 09 章：一致性与共识

> 本章目标：理解**线性一致性**等保证的代价，以及 **2PC、Raft** 在系统中的作用边界。

## 初学者先抓住一句话

**共识**让多个节点对单一决定达成一致；**强一致**很贵，多数业务在 **因果/最终一致** 上更划算。

## 一致性保证

| 级别 | 说明 |
|---|---|
| 最终一致 | 停止写入后，最终所有副本相同 |
| 因果一致 | 有因果关系的操作顺序一致 |
| 线性一致 | 实时全局顺序，像单副本 |

**线性一致** 典型用途：锁、唯一约束、拍卖出价；**不是**默认目标。

## 顺序保证

- **单分区** 内：日志天然全序（Kafka 分区内）。
- **全局序**：需 **Total order broadcast**（Raft/Zab 日志）。
- **版本向量**：检测并发冲突（多主、CRDT）。

## 分布式事务与共识

### 两阶段提交 2PC

```text
Prepare → 所有参与者投票
Commit/Abort → 协调者决定
```

- **阻塞**：协调者挂掉时参与者等待。
- **XA**：2PC 工业标准；跨 DB 性能差，慎用。

### 三阶段 / Saga

- Saga：**本地事务 + 补偿**，无全局锁，最终一致。
- 适合长流程微服务（订单 → 库存 → 支付）。

### 共识算法 Raft

- **选主 + 日志复制**；过半确认即提交。
- 应用：etcd、Consul、TiKV Meta。
- **Fencing**：新 leader 带更大 epoch，存储拒绝旧 epoch 写。

## 架构设计检查清单

- [ ] 是否把「强一致」写进 SLA 但未测延迟成本？
- [ ] 跨 5 个服务的 2PC 是否可改为 Saga + 对账？
- [ ] 分布式 ID 是否依赖可回拨时钟？
- [ ] Leader 选举与业务写是否共用同一套认知？

## 与 Java 后端

- **Seata AT**：近似 2PC + undo log；理解失败与超时。
- **RocketMQ 事务消息**：半消息 + 回查，实现本地消息表模式。
- **Outbox + Debezium**：本地事务写业务+Outbox，异步投递。
- **etcd / Nacos**：配置与选主，理解 Raft 延迟。

## 本章小结

- CAP 简化论争；实际在分区时做细粒度权衡。
- 共识是复制状态机的基础；2PC 与 Saga 各适不同边界。
- 设计从「业务能否接受旧读/重试/对账」倒推一致级别。
