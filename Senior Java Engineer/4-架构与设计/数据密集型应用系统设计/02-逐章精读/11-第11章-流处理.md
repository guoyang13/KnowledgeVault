# 第 11 章：流处理

> 本章目标：理解**事件流**作为一等公民，以及 CDC、流批一体与「数据库 + 日志」统一模型。

## 初学者先抓住一句话

**日志（Log）** 是持久、追加、分区的事件序列；**流处理**是对无界日志的持续计算。

## 传递事件流

| 模式 | 说明 |
|---|---|
| 消息代理 | RabbitMQ：队列消费即删 |
| **日志 broker** | Kafka：持久、可重放、多消费者组 |

**对比**：

- 队列：任务分发，单消费者。
- 日志：数据集成，**回溯历史**、**衍生多视图**。

## 数据库与流

### 变更数据捕获 CDC

- 读 DB **事务日志**（binlog、WAL），推送到 Kafka。
- 解决 **双写问题**：只写 DB，索引/缓存由 CDC 更新。

### 事件溯源 Event Sourcing

- **状态 = 事件折叠**；真相是事件链而非当前行。
- 与 CQRS 常配合：写模型事件化，读模型物化。

### 时间与窗口

- **事件时间** vs **处理时间**；乱序需 watermarks。
- 窗口：滚动、滑动、会话窗口。

## 流处理

| 语义 | 实现思路 |
|---|---|
| At-most-once | 可能丢 |
| At-least-once | 可能重复，需幂等 |
| Exactly-once | 事务性写入 + 幂等 + 去重（端到端难） |

引擎：Flink、Kafka Streams、Spark Streaming。

## 架构设计检查清单

- [ ] 是否应用双写 DB + ES 无补偿？
- [ ] 消费者是否幂等（业务键 dedup）？
- [ ] 消息是否可重放做灾备或新视图？
- [ ] 全局顺序是否误用单分区 Kafka 成为瓶颈？

## 与 Java 后端

- **RocketMQ / Kafka**：事务消息、顺序消息、延迟消息。
- **Canal / Debezium**：MySQL binlog → MQ → 更新 Redis/ES。
- **Transactional Outbox**：同库写 `outbox` 表，Poller 发 MQ。
- **Flink CDC**：实时数仓入湖。

## 本章小结

- 流不是「小批处理」，而是不同的系统语义（无界、乱序、状态）。
- CDC + 日志是微服务数据同步的成熟模式。
- Exactly-once 是目标，工程上常 **at-least-once + 幂等**。
