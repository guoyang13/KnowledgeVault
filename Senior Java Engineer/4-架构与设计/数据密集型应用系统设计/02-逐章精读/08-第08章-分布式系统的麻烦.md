# 第 08 章：分布式系统的麻烦

> 本章目标：建立分布式**不可假设**清单——网络、时钟、进程都会说谎。

## 初学者先抓住一句话

单机程序可以假设「要么成功要么抛异常」；分布式里 **部分失效** 是常态，**超时不能证明任何事**。

## 故障与部分失效

- 整台机器挂：相对好处理（健康检查摘除）。
- **慢响应、丢包、半开连接**：最难，常导致重复提交、脑裂。

## 不可靠的网络

- 延迟 **无上限**；不能设「3 秒必死」就当节点死了。
- **TCP 有时能检测**，应用层仍可能卡住。
- 设计：**幂等**、**超时 + 重试 + 退避**、**熔断**、**限流**。

## 不可靠的时钟

| 时钟类型 | 问题 |
|---|---|
| 墙上时钟 Time-of-day | NTP 跳变，不适合排序 |
| 单调时钟 Monotonic | 只适测间隔，不能跨节点比较 |

### 进程暂停

- GC STW、虚拟机冻结、磁盘 thrashing。
- **Lease 过期** 时进程仍以为自己持有锁 → 用 **Fencing token**（第 9 章）。

## 知识、真相与谎言

- **FLP 结果**：异步网络中确定性共识不可能（若允许一个节点崩溃）。
- **拜占庭故障**：节点任意行为；区块链外少见。
- **系统模型**：同步 vs 部分同步 vs 异步 —— 决定算法可行性。

## 实践准则

```text
1. 不要依赖跨节点时钟排序业务事件
2. 超时后：重试可能 duplicate → 需要幂等键
3. 健康检查 + 优雅下线 + 连接 draining
4. 监控：延迟分布、丢包、GC 日志
5. 混沌测试：网络分区、延迟注入
```

## 架构设计检查清单

- [ ] 分布式锁是否无 fencing，过期 leader 仍写 S3/DB？
- [ ] 是否用 `System.currentTimeMillis()` 做订单号/排序？
- [ ] RPC 超时是否引发级联重试风暴？
- [ ] JVM Full GC 是否导致注册中心误判下线？

## 与 Java 后端

- **Hystrix / Resilience4j**：超时、熔断、舱壁。
- **雪花 ID**：依赖时钟，需处理时钟回拨。
- **Redisson 锁**：注意 lease 与 watchdog；关键资源加 token 校验。
- **K8s liveness/readiness**：与 GC 停顿协调 probe 阈值。

## 本章小结

- 分布式复杂性来自部分失效与不确定性。
- 时钟与超时是 bug 温床；用版本号/逻辑时钟代替墙上时钟排序。
- 为「重复、乱序、延迟」设计，而非假设理想网络。
