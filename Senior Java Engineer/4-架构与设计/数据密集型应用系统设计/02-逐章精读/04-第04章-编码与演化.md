# 第 04 章：编码与演化

> 本章目标：掌握服务升级、多版本共存时，**数据格式与 Schema 如何向前/向后兼容**。

## 初学者先抓住一句话

应用会频繁升级，**存储与消息中的数据格式**必须能演化，否则每次发版都是数据库迁移灾难。

## 编码格式对比

| 格式 | 结构 | 演化 | 场景 |
|---|---|---|---|
| JSON / XML | 文本、自描述 | 灵活但无强制 Schema | REST API、配置 |
| Protocol Buffers | 二进制 + .proto | 字段编号，易兼容 | gRPC、内部 RPC |
| Avro | 二进制 + Schema | 读写分离 Schema，紧凑 | Kafka、Hadoop |
| Thrift | 类似 Protobuf | 多协议 | 跨语言 RPC |

### 兼容性规则（Protobuf / Avro 通用思想）

- **添加字段**：新代码写新字段，旧代码忽略 → 向后兼容读。
- **删除字段**：保留字段号不用 → 避免误解析。
- **不要改字段号/类型**。

## 数据流的类型

### 1. 数据库通过服务（REST/RPC）

- 服务层做 **编码/解码**；DB 存行或 JSON。
- 风险：多服务读同一表，Schema 变更需协调。

### 2. 服务间异步消息

- 消息队列 + **Schema Registry**（Confluent）。
- 消费者与生产者可独立升级。

### 3. 持久化事件日志

- Kafka 日志作为 **系统真相源**（联系第 11 章）。
- 重放历史需 Schema 版本链。

## 模式演化策略

| 策略 | 说明 |
|---|---|
| Schema-on-write | DB 迁移脚本（Flyway/Liquibase） |
| Schema-on-read | 应用层兼容多版本字段 |
| 双写 / 扩列 | 大表迁移：加列 → 双写 → 切读 → 删旧 |

## 架构设计检查清单

- [ ] API 是否暴露内部 DB 字段结构（阻碍演化）？
- [ ] Kafka 消息是否有 Schema 版本与兼容策略？
- [ ] 移动端 / 老客户端是否仍在访问旧 API？
- [ ] 是否用「删列改类型」而非「加新列迁移」？

## 与 Java 后端

- **Protobuf + gRPC**：微服务间契约；`.proto` 进 CI 做 breaking change 检测。
- **Jackson `@JsonIgnoreProperties(ignoreUnknown = true)`**：API 向前兼容。
- **Flyway**：SQL Schema 版本化，与代码发版绑定。
- **Avro + Kafka**：大数据链路常用；Spring Kafka + Schema Registry。

## 本章小结

- 演化能力是可维护性的核心。
- 编码格式选择影响性能、兼容性与工具链。
- 数据流路径（DB/RPC/MQ）决定谁来承担兼容逻辑。
