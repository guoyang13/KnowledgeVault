# 性能指标与容量规划：RocketMQ、MySQL、Redis、SelectDB

> 目标：用统一方法理解消息队列、交易数据库、缓存和实时数仓的性能，避免把不同组件的“TPS/QPS”直接横向比较。

## 一页结论

| 组件 | 首要职责 | 核心性能口径 | 不应拿它衡量什么 |
| --- | --- | --- | --- |
| RocketMQ | 异步传递、削峰、解耦 | 消息收发 TPS、堆积量、端到端延迟 | 下游数据库已完成写入的速度 |
| MySQL | 交易事实、强一致事务 | 业务事务 TPS、QPS、P95/P99、锁等待、IOPS | 大规模聚合分析吞吐 |
| Redis | 热点数据的低延迟访问 | OPS/QPS、P95/P99、命中率、内存与淘汰 | 最终一致的持久化事实 |
| SelectDB | 实时分析、报表、检索 | 写入行数/秒或 MB/s、查询并发、扫描量、查询延迟 | 短事务提交能力 |

**核心原则：** 一个“订单创建”可能是 MySQL 的 1 笔事务、RocketMQ 的多条收发操作、Redis 的多条读写命令、SelectDB 的多行明细写入。它们的 TPS 不可直接相等或相加。

## 1. 先统一术语

### QPS、TPS、OPS

- **QPS (Queries Per Second)**：每秒查询/请求数。数据库中常表示 SQL 数；Redis 中常等同于命令数。
- **TPS (Transactions Per Second)**：每秒事务数。MySQL 指提交的业务事务；RocketMQ 通常指每秒消息发送或消费操作，需确认控制台统计口径。
- **OPS (Operations Per Second)**：每秒操作数，Redis 常用，通常等同于命令 QPS。
- **P95/P99 延迟**：95%/99% 请求不超过的响应时间。相比平均值，更能发现排队、慢命令与长尾问题。

### 端到端容量链路

```text
用户请求
  -> Redis（缓存命中/未命中）
  -> MySQL（交易提交）
  -> Binlog / CDC（捕获数据变更）
  -> RocketMQ（传递与削峰）
  -> 消费者
  -> SelectDB（实时分析可见）
```

每一段都要独立监控和限流。MQ 消费速度不能超过 MySQL 或 SelectDB 的稳定处理能力；否则只是把“请求高峰”转化成“消息积压”。

## 2. RocketMQ：看消息吞吐和积压，不只看 TPS

### 关键指标

| 指标 | 含义 | 关注信号 |
| --- | --- | --- |
| 生产 TPS | 每秒发送消息数 | 是否接近实例规格或生产端瓶颈 |
| 消费 TPS | 每秒成功消费消息数 | 应长期不低于生产 TPS |
| 消息堆积量 / 堆积时长 | 未消费消息与最早消息等待时间 | 持续增长表示下游处理能力不足 |
| 发送/消费 P99 延迟 | 投递、拉取、处理确认的尾延迟 | 峰值时显著抬升通常意味着排队或限流 |
| 重试、死信消息数 | 消费失败后的重试与死信 | 说明幂等、依赖或数据质量有问题 |
| Topic/队列分布 | 消息是否均匀落到队列 | 单分区热点会限制并行消费 |

### 口径陷阱

RocketMQ 的吞吐是**消息操作**，不是业务订单数。例如一个订单事件可能有：1 次发送、2 个消费组各消费 1 次，即至少产生 3 次消息操作。增加消费组会增加消费吞吐，但不提升同一消费组内单一队列的顺序消费能力。

### 消费端设计动作

- 消费并发由下游容量决定，而不是盲目拉满。
- 以 `业务主键 + 事件类型` 作为幂等键；消息系统通常按至少一次投递设计。
- 对允许合并的写入进行批处理，设置最大批次、最大等待时间和失败回退。
- 监控“最早未消费消息的年龄”，它比单纯堆积条数更能反映业务影响。
- 当消费 TPS 小于生产 TPS 时：先限流或扩容消费端，再确认数据库、网络和下游依赖是否成为瓶颈。

## 3. MySQL：看业务事务、延迟、锁与磁盘

### 关键指标

| 指标 | 含义 | 经验目标 |
| --- | --- | --- |
| 业务 TPS | 已提交事务数/秒 | 用真实事务定义，不用单条 SQL 替代 |
| QPS | 每秒 SQL 执行数 | 与 TPS 联合看，`QPS / TPS` 反映事务 SQL 数量 |
| P95/P99 响应时间 | 查询与事务提交长尾 | 先以业务 SLA 定目标 |
| CPU、内存、IOPS、磁盘吞吐 | 实例资源消耗 | 持续峰值建议保留约 30% 余量 |
| 活跃连接、连接池等待 | 是否因连接过多排队 | 连接数不是越大越好 |
| 行锁等待、死锁、慢 SQL | 并发冲突与 SQL 效率 | 任何持续上升都需定位 |
| Buffer Pool 命中率 | 热数据是否主要从内存读取 | 热点 OLTP 通常期望接近 99% |
| 主从复制延迟 | 读写分离下副本是否陈旧 | 强一致读取不可依赖延迟副本 |

### 起步规格与容量思路

| 场景 | 可作为起步配置 | 规划目标 |
| --- | --- | --- |
| 测试/后台系统 | 2C4G 或 2C8G，PL1 | 写 TPS 小于 100 |
| 小型生产 | 4C16G，高可用、独享型，PL1/PL2 | 混合事务 100-1,000 TPS |
| 核心 OLTP | 8C32G 或 16C64G，高可用、独享型，PL2/PL3 | 1,000-5,000 TPS，必须实测 |

以上是容量规划的起点，不是厂商承诺。同样的实例，单行主键更新和多表关联、二级索引维护、热点库存扣减的 TPS 可能相差一个数量级。

### 设计动作

- 每个高频查询都应有可验证的索引与 `EXPLAIN` 结果。
- 避免长事务、热点行、无界范围扫描和大批量同步 DML。
- 应用使用连接池，限制并发连接而非直接让请求无限进入数据库。
- 读多写少可加只读副本；写入瓶颈优先优化事务与模型，必要时分库分表或改用更适合的分布式方案。

## 4. Redis：看尾延迟、命中率和内存压力

### 阿里云 Tair（兼容 Redis）公开性能参考

以下为阿里云 8GB、标准双副本、同 VPC、单命令压测的参考值；它们是极限性能而非生产承诺。

| 命令 | Redis 开源版 QPS / P99 | Tair 内存型 QPS / P99 |
| --- | ---: | ---:|
| `GET` | 204,690 / 0.47ms | 519,761 / 0.36ms |
| `SET` | 142,376 / 0.72ms | 282,656 / 0.86ms |
| `HGET` | 188,903 / 0.52ms | 494,603 / 0.37ms |
| `HSET` | 124,613 / 0.97ms | 260,069 / 1.03ms |
| `ZADD` | 113,135 / 0.78ms | 208,169 / 1.14ms |

生产容量通常先按该类压测结果的 50%-70% 规划，并用真实 Key 数、Value 大小、读写比和网络拓扑复测。

### 关键指标

| 指标 | 含义 | 经验目标 |
| --- | --- | --- |
| OPS/QPS | 每秒 Redis 命令数 | 按命令类型、读写分开观察 |
| P95/P99 延迟 | 命令的尾延迟 | 缓存场景常以 P99 小于 1-2ms 为目标 |
| 内存使用率 | 已用内存与 `maxmemory` 的比例 | 建议保留 20%-30% 缓冲 |
| 命中率 | `hits / (hits + misses)` | 一般缓存大于 90%，核心热点常大于 95% |
| `evicted_keys` | 因内存压力被淘汰的 Key 数 | 持续增长需要扩容或调整策略 |
| 带宽与连接数 | 网络与连接池是否成为瓶颈 | 关注突增和饱和 |
| 主从延迟 | 副本数据滞后 | 读写分离场景必须监控 |
| Slowlog、大 Key、热 Key | 单命令阻塞或单分片倾斜 | 是尾延迟恶化的常见根因 |

### 常见性能陷阱

- 大 Key 或超大集合：单次序列化、网络传输和释放内存都会阻塞事件循环。
- 热 Key：单个分片先到达上限，集群扩容也未必解决问题。
- 慢命令：避免 `KEYS`，大集合遍历使用 `SCAN` 系列命令；审慎使用长 Lua 脚本。
- 内存触顶：淘汰和内存碎片整理会抬升写延迟。
- 持久化：RDB/AOF、主从同步会影响尾延迟，关键路径需验证故障和重写期间的表现。

## 5. SelectDB：看分析吞吐与查询长尾

SelectDB 是实时 OLAP / 实时数仓。它兼容 MySQL 协议，但不应以 MySQL 事务 TPS 评价。

### 关键指标

| 指标 | 含义 |
| --- | --- |
| 导入行数/秒、MB/s | 数据写入吞吐 |
| 导入可见延迟 | 数据从进入系统到可查询的时间 |
| 查询并发、QPS | 并行分析或服务查询能力 |
| P95/P99 查询延迟 | 看板、接口或即席查询的业务体验 |
| 扫描行数/字节数 | 查询代价，决定扩容与优化方向 |
| Compaction/版本积压 | 写入后合并与元数据是否跟上 |
| CPU、内存、磁盘与缓存命中 | 计算与数据访问是否达到瓶颈 |

### 公开基准参考

官方 SSB 基准在 64C/512GB、800GB 高性能盘环境中：100GB 数据集的 13 条标准查询合计 1.72 秒，500GB 数据集为 20.15 秒。该结果适合比较分析引擎能力，不能替代真实业务压测。

### 设计动作

- 依据查询时间范围做分区，依据并行度和数据量做分桶。
- 让高频过滤字段和排序键匹配；按需使用倒排、Bloom Filter 或物化视图。
- 写入与看板/即席分析拆分计算集群，避免资源抢占。
- 用 CDC 将 MySQL 变更实时同步到 SelectDB，避免业务代码双写造成不一致。

## 6. CDC、MQ 与下游数据库的容量校验

### CDC 是什么

- **Binlog（Binary Log，二进制日志）**：MySQL 记录数据变更的日志。
- **CDC（Change Data Capture，变更数据捕获）**：持续读取 Binlog，将 `INSERT`、`UPDATE`、`DELETE` 转成事件并同步到下游。

典型链路：`MySQL -> Binlog -> CDC（DTS / Canal / Flink CDC）-> RocketMQ -> 消费者 -> SelectDB`。

### 不做双写

不推荐业务代码在同一请求中既写 MySQL 又写 SelectDB/MQ：任一步骤失败都会产生不一致。更可靠的做法是先以 MySQL 事务为事实来源，再用 CDC 异步传播变更。

### 容量校验公式

设业务峰值为 `B` 笔事务/秒，每笔产生 `E` 条 CDC 事件，每条事件平均 `S` 字节：

```text
CDC / MQ 生产消息数 = B * E
CDC / MQ 生产带宽   = B * E * S
消费端最低处理能力  > B * E（需预留峰值与重试余量）
```

若一个事件会被 `G` 个消费组分别消费：

```text
MQ 消费操作数 = B * E * G
```

这解释了为什么“MQ 2,000 TPS”不能简单推导为“数据库能承受 2,000 TPS”。

### 7.1 RocketMQ：将购买规格换算为业务容量

阿里云 RocketMQ 的 TPS 是服务端**消息收发之和**，以 4KB 普通消息为一个计算单位。假设每秒产生 `1,000` 个订单变更事件，且有 2 个消费组：

```text
生产 = 1,000 次/秒
消费 = 1,000 * 2 = 2,000 次/秒
RocketMQ 收发合计 = 3,000 TPS
```

因此，一个 `2,000 TPS` 的实例不足以覆盖该例子。若消息为 8KB，或使用事务/定时等高级消息，还要按产品的计算倍率折算。超规格时服务端直接返回失败，而不是替应用排队；生产者必须配置重试并在峰值留余量。

### 7.2 RDS MySQL：内存命中与磁盘 I/O 是两条不同的基线

以下数据来自阿里云 MySQL 8.0 高性能本地盘白皮书，均为高可用通用型、20 分钟 SysBench 测试。标准读写事务中每笔事务包含 18 条 SQL，因此 QPS 与 TPS 不能直接视作两种独立的业务流量。

| 规格     |   内存命中：QPS / TPS | 磁盘 I/O 型：QPS / TPS | 压测 IOPS |
| ------ | ---------------: | -----------------: | ------: |
| 1C2G   |      7,779 / 389 |         1,151 / 58 |   1,000 |
| 2C4G   |   21,524 / 1,076 |        2,606 / 130 |   2,000 |
| 4C16G  |   86,709 / 4,335 |        9,072 / 454 |   7,000 |
| 8C32G  |  157,117 / 7,856 |       15,557 / 778 |  12,000 |
| 16C64G | 244,204 / 12,210 |       18,173 / 909 |  14,000 |

云盘实例还受规格、盘类型和容量共同限制。例如 ESSD 的实际 IOPS 上限为 `min(容量基准 IOPS, 盘等级上限, 实例上限)`；不能只根据 CPU/内存判断 MySQL 的写入能力。

### 7.3 Tair / Redis：先核算带宽，再看 QPS

以 Redis 开源版标准双副本为例，8GB 规格提供约 80,000 QPS、192Mbps（24MB/s）双向带宽和 20,000 最大连接数。若平均响应包约 2KB，仅读流量达到 80,000 QPS 时理论下行会达到约 156MB/s，远超 24MB/s；此时网络带宽会先成为瓶颈。

```text
近似带宽（MB/s）= QPS * 平均请求或响应字节数 / 1024 / 1024
```

实际核算时应分别计算上行（请求 + 写入 Value）与下行（响应 + 读取 Value），并为复制流量和峰值预留余量。集群版在 Key 均匀时可随分片近似横向扩展；热 Key 会使扩容效果失真。

### 7.4 SelectDB：基线用于分析，不用于交易承诺

SelectDB 官方 SSB 基线来自单一 `64C/512GB` 仓库、`800GB` 高性能云盘和特定版本内核。它展示了宽表聚合、星型 Join 的分析性能，而不是持续写入能力或业务接口 QPS。

对实际项目应另行设定并压测：

- 数据写入行数/秒、单批大小、数据可查询延迟。
- 看板 SQL 的 P95/P99 与并发数。
- 高频过滤字段的索引、分区分桶与是否存在数据倾斜。
- 写入、实时看板、即席分析是否隔离到不同计算集群。

## 8. 压测与告警清单

### 压测步骤

1. 用接近生产的数据量、字段长度、索引、Key 分布和读写比例构造环境。
2. 先压单组件，记录吞吐与 P95/P99；再压端到端链路。
3. 从预计峰值开始，逐步提升到峰值的 1.5-2 倍。
4. 在稳定压力下至少观察 30 分钟，同时覆盖缓存淘汰、数据库慢查询、MQ 堆积和 SelectDB Compaction。
5. 复测故障场景：Redis 主从切换、MySQL 慢 SQL 或副本延迟、消费者重启、MQ 重试。

### 最小告警集

| 组件 | 建议告警 |
| --- | --- |
| RocketMQ | 堆积时长持续增长、消费 TPS 小于生产 TPS、死信/重试突增 |
| MySQL | P99 上升、CPU/IO 长时间高位、慢 SQL、锁等待/死锁、连接池等待、复制延迟 |
| Redis | P99 上升、内存高位、淘汰增长、命中率下降、大 Key/热 Key、复制延迟 |
| SelectDB | 导入延迟、查询 P99、失败率、Compaction/版本积压、读写资源争用 |
