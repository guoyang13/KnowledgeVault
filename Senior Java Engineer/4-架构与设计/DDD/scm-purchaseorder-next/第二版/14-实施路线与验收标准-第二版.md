# 实施路线与验收标准（第二版）

## 1. 实施原则

不按 Controller 或数据表逐个搬迁，而是按可独立验收的业务闭环迁移。每个切片都同时具备用例、领域模型、持久化、事件、监控和回滚能力。

## 2. 推荐切片

### 切片 0：契约与事实基线

交付：

- 旧接口、MQ、表和调用方清单。
- 旧 PO 类型和状态组合样本。
- 生产数据分布与非法状态统计。
- 新旧字段映射和事件字典。
- 关键链路 Trace 基线。

退出条件：

- 关键接口调用方覆盖率 100%。
- 所有状态编码都有业务解释和来源。
- 找出绕过 Service 直接写 PO/PSO 表的任务或脚本。

### 切片 1：PR 转 PO 草稿与提交审批

范围：

- 商品类采购的一个低风险路线。
- 从 PR 明细选择、生成 PO 草稿、编辑、提交和审批结果回写。
- 暂不接管发货、入库、装柜、商检和结算。

这是首选切片，因为它能够验证最关键的采购承诺模型，同时避免一次接入所有履约系统。

退出条件：

- 相同 `commandId` 重试只生成一张 PO。
- PR 转单数量不超卖。
- 新旧订单金额、税额、数量和路线映射一致。
- 审批回调重复或乱序不会错误变更订单。
- PO 生效事件可重放。

### 切片 2：草稿和审批路线扩展

逐步接入九种旧 PO 类型对应的路线组合。每增加一种路线，只新增路线规则和必要端口，不复制完整订单 Service。

退出条件：

- 全部路线通过同一套订单状态机。
- 路线差异由策略测试覆盖。
- 旧 `poType` 只存在于兼容层和迁移字段。

### 切片 3：交期变更、调价和终止

将三个独立生命周期从旧 `PurchaseOrderService` 中迁出。

退出条件：

- 所有生效后修改均有变更单和审计记录。
- 调价事件能驱动结算重算。
- 终止规则能区分未发货、部分履约和已履约数量。

### 切片 4：履约要求与任务

PO 生效后生成履约要求计划，先接入样图、资质、约仓三个高频任务，再扩展装柜、对样和质检。异常、超期和跟单作为任务或里程碑偏离计划后的协同行为一起迁入。每项要求必须保存规则版本、判断原因、作用范围和阻塞节点。

退出条件：

- 相同 PO 版本重复处理只生成一个有效要求计划。
- “需要/不需要”均可追溯到规则和输入快照。
- 任务状态不复制并覆盖外部业务对象的真实状态。
- 豁免操作具有原因、操作人和审批记录。
- 任务超时能生成唯一异常事项，并完成分派、升级、提醒和关闭。

### 切片 5：履约事实与订单旅程投影

消费供应商、物流、仓储和客户交付事件，形成订单行履约投影。旧综合状态继续由兼容层计算，不能反向成为新模型真相。

退出条件：

- 事件重复、乱序和延迟测试通过。
- 投影可从事件重建。
- 分批发运能够显示各批次节点、总体阶段和阻塞任务。
- 新旧页面履约摘要差异可观测。

### 切片 6：查询、导出和看板

将旧大 Service 中的查询拼装迁到 Query Model。导入导出只负责输入输出，不承载领域规则。

退出条件：

- 主要页面 P95 和错误率不劣于旧服务。
- 导出数据与新读模型一致。
- 查询侧不加载并修改聚合。

### 切片 7：对样与质检迁入

将 `scm-order-service` 中的对样和质检能力迁入新服务的 `qualityinspection` 模块。先迁采购订单来源，再迁装柜明细和仓间调拨来源。

退出条件：

- 新旧质检单、明细、拒收数量、附件和状态差异达到约定阈值。
- 对样和质检状态机由新质量聚合维护，不再写入 PO 综合状态。
- 质检事件可驱动履约协同、仓储处置、结算和查询投影。
- 新模块成为唯一写入方，旧接口通过兼容层提供服务。

### 切片 8：外部上下文边界收口

依次迁移或明确归属：

- 装柜与跨境物流。
- 商检与资质。
- 仓储收货、入库与库存。

这些能力可以留在各自服务，但与新 PO 只通过 API/事件协作。

## 3. 新旧并行方案

### 3.1 写入归属

每个业务租户、采购组织或 PO 路线只有一个写入主系统：

```text
route_key -> OLD | NEW
```

禁止同一命令同时由新旧系统作为主写。影子侧只计算结果和记录差异。

### 3.2 数据同步

- 旧到新：CDC/事件转换为初始化或兼容投影。
- 新到旧：发布兼容事件或由同步器更新旧读模型。
- 同步数据携带 `source_system`、`source_version`、`last_event_id`。
- 发现冲突时停止覆盖并进入差异队列。

### 3.3 回滚

- 切片开关按组织和路线生效。
- 新写入切回旧系统前，先确认增量同步水位。
- 已由新系统生成的 PO 保持新系统主写，不在生命周期中途切换主系统。
- 回滚只回流量，不删除新库数据和事件。

## 4. 数据迁移

迁移顺序：

1. 字典、供应商、组织和地点快照映射。
2. PO 头和订单行。
3. 审批实例与变更单。
4. 履约摘要。
5. 查询投影。

旧状态转换示例：

| 旧状态 | 新订单状态 | 新履约摘要 |
|---|---|---|
| 草稿 | DRAFT | NOT_STARTED |
| 待审核 | APPROVAL_PENDING | NOT_STARTED |
| 已驳回 | REJECTED | NOT_STARTED |
| 待定柜/供应商待发货 | EFFECTIVE | DELIVERY_PENDING |
| 供应商已发货 | EFFECTIVE | SHIPPED |
| 中国仓/海外仓入库完成 | EFFECTIVE 或 COMPLETED | INBOUNDED |
| 三类已作废 | CANCELLED 或 TERMINATED | 保存作废时履约快照 |

转换不能只看状态值，还必须结合 PO 类型、PSO 数量、入库记录和作废时间。

## 5. 观测指标

- 命令成功率、P95、P99。
- 聚合乐观锁冲突率。
- outbox 未发送数量和最大滞留时间。
- inbox 重复事件数、乱序事件数和处理失败数。
- PR 预占超时数量。
- 新旧金额、数量、状态和履约摘要差异率。
- 审批待发起、待回调和异常实例数量。
- 投影事件水位和延迟。

## 6. 完成标准

### 领域

- 订单状态只表达采购承诺生命周期。
- PO 聚合内无 WMS、库存、物流和结算调用。
- 所有生效后修改都有独立业务单据和审计记录。

### 架构

- domain 模块无 Spring、MyBatis、Feign、MQ 依赖。
- Repository 只负责聚合持久化。
- 命令与查询模型分离。
- 关键集成全部具有 outbox/inbox、幂等和重试。

### 迁移

- 连续观察期内核心字段差异率达到约定阈值。
- 无未识别调用方和直接写旧表任务。
- 每个切片都有独立开关、回滚手册和负责人。
- 旧服务下线后仍保留审计数据和事件重放能力。
