# 采购订单服务 DDD 第二版：设计结论与现状审计

## 1. 文档定位

第一版解决的是“如何用新服务逐步替换旧服务”，第二版继续回答两个更基础的问题：

1. 采购订单服务真正应该负责什么。
2. 哪些对象必须强一致，哪些业务只能通过事件协作。

第二版以原 `scm-procurement-service` 代码为事实基线。第一版的影子运行、分流和下线方案仍然有效，但领域边界与聚合模型以本文及后续第二版文档为准。

## 2. 核心结论

### 2.1 服务边界

新服务的核心职责定义为：

> 管理企业向供应商下达的采购承诺，以及采购承诺的审批、变更和终止。

新服务可以保存履约摘要，但不拥有仓库收货、库存入库、出口装柜、商检、销售交付和应付结算的业务事实。

### 2.2 聚合边界

- `PurchaseOrder`（采购订单）是采购承诺聚合根。
- 旧 `PSO` 不是“子订单聚合”，其数据结构实际是一条 SKU 采购明细。第二版将其命名为 `PurchaseOrderLine`（采购订单行）。
- 订单行在草稿和审批阶段属于 `PurchaseOrder` 聚合，但履约数量不直接写回订单聚合。
- `PurchaseRequisition`（采购需求）、`DeliveryDateChange`（交期变更单）、`PriceAdjustment`（调价单）分别是独立聚合。
- 货柜、商检、入库、差异、结算属于其他限界上下文，只通过编号和集成事件关联。

### 2.3 状态模型

旧 `purchase_order_status` 同时表达审批、装柜、发货、收货、入库等状态，不能继续作为新领域模型的唯一状态。

第二版拆为：

- `orderStatus`：采购承诺的生命周期。
- `approvalStatus`：审批流程投影。
- `fulfillmentSummary`：履约上下文投影出的摘要。
- `changeStatus`：交期、价格、作废等变更单自身状态。

### 2.4 一致性

- 聚合内使用本地事务和乐观锁保证强一致。
- 跨上下文只保证最终一致。
- 领域事件与业务数据通过 transactional outbox（事务发件箱）同事务落库。
- 消费端通过 inbox（收件箱）或唯一消费键保证幂等。
- 不允许在 `afterCommit` 回调中承担不可丢失的关键业务更新。

## 3. 原服务审计

### 3.1 规模

基于当前代码扫描：

| 项目 | 数量 |
|---|---:|
| Java 源文件 | 1046 |
| Controller | 23 |
| Service | 109 |
| Repository | 38 |
| 数据表 | 37 |
| MQ Consumer | 15 |
| 外部 Adapter | 42 |

典型大类：

| 类 | 规模 | 暴露的问题 |
|---|---:|---|
| `PurchaseOrderService` | 约 3993 行 | 查询、转单、入库、差异、导入和报表混合 |
| `PrDraftService` | 约 3589 行 | 需求计算、审批、导入和异常处理混合 |
| `PoDataCutoverService` | 约 2029 行 | 迁移逻辑进入长期业务服务 |
| `PoCommodityInspectionService` | 约 1854 行 | 商检与采购订单边界不清 |
| `PurchaseOrderExportService` | 约 1842 行 | 出口履约成为采购订单内部能力 |

这些数字不是拆服务的直接依据，但说明旧服务已经按技术功能增长，而不是围绕业务一致性边界演进。

### 3.2 状态耦合

`PoStatusEnum` 包含：

- 草稿、待审核、待确认、已驳回。
- 待定柜、供应商待发货、供应商已发货。
- 中国仓收货与入库、发往海外。
- 海外仓或门店收货与入库、客户收货。
- 三种按阶段区分的作废状态。

这实际上把至少四条状态轴压成了一条线：

1. 采购订单审批。
2. 供应商履约。
3. 跨境物流。
4. 仓储与最终交付。

直接后果是状态转移依赖订单类型，取消逻辑也要按当前履约阶段选择不同的作废编码。

### 3.3 事务边界混乱

旧 `PurchaseOrderRepository` 不仅持久化数据，还负责：

- 审批通过后的业务分支。
- 同步修改所有 PSO 状态。
- 发布 Spring 事件。
- 读取框架用户上下文。

`PoStatusChangeListeners` 在事务提交后继续更新 PRD 绩效、超期批次、调价记录和通知记录。这里存在三个风险：

- 监听失败后主事务已经成功，业务状态可能永久不一致。
- 同一个 PO 状态变化触发多个不同领域的副作用，难以单独重试。
- 通过状态值推断业务事实，无法识别事件来源和重复事件。

### 3.4 分层问题

旧工程虽然有 `domain`、`dal`、`dependency` 等模块，但 `domain` 模块依赖：

- `dal`
- `interface`
- `dependency`

领域对象还直接执行 DO/DTO 转换。这是“按目录分层”，不是六边形架构。正确方向是领域模块只依赖 JDK 和领域共享内核，基础设施依赖领域端口。

### 3.5 真实业务边界线索

代码已经自然长出了多个独立业务概念：

- PRD 草稿与采购需求。
- PO 审批与供应商确认。
- 交期变更单。
- 调价单。
- 采购商检单。
- 采购货柜与装柜明细。
- 费用与结算处理。
- 超期、异常和跟单提醒。

它们有独立编号、状态、表和操作入口，应被视为聚合或限界上下文候选，而不是继续作为 `PurchaseOrderService` 的方法集合。

## 4. 第一版需要修正的内容

| 第一版设计 | 第二版修正 |
|---|---|
| `PurchaseOrder` 聚合内包含 `PurchaseSubOrder` 并控制其全部履约状态 | `PurchaseSubOrder` 重命名为订单行；履约状态从聚合中移出 |
| `PurchaseOrder` 直接执行发货、收货和入库行为 | 采购域接收外部履约事件，仅维护履约摘要 |
| 采购订单上下文包含 PO/PSO/发货/收货/入库 | 采购承诺与履约执行分离 |
| 订单审批通过后直接推送多个下游 | 由可靠事件和流程管理器编排 |
| 以订单类型派生多套 Service 策略 | 使用 `ProcurementRoute` 值对象和策略规则，避免复制整个生命周期 |
| 按接口批次逐步迁移 | 优先按完整业务闭环迁移，接口只是流量入口 |
