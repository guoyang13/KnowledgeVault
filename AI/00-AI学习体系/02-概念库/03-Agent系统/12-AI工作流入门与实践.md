# AI 工作流入门与实践

> 更新时间：2026-07-10。
> **AI 工作流**是把大模型嵌进「有顺序、可重复、可分支」的业务步骤里，而不是每次从零聊天。
>
> **定位**：工作流的入门主笔记，侧重应用场景、五种模式、选型和落地原则；不展开框架实现。
>
> 深入：[[AI/00-AI学习体系/02-概念库/03-Agent系统/11-AI工作流-Graph与Loop|AI工作流-Graph与Loop]] · 前置：[[AI/00-AI学习体系/02-概念库/03-Agent系统/01-Workflow vs Agent|Workflow vs Agent]] · 导航：[[AI/00-AI学习体系/02-概念库/03-Agent系统/00-Agent系统导航|Agent系统导航]]

## 一句话

```text
AI 工作流 = 业务流程 + AI 节点 + 判断/工具/人工卡点
```

像流水线：每一步做什么、失败怎么办、要不要人审，都事先定好。

---

## 和传统自动化的区别

| | 传统工作流（RPA/脚本） | AI 工作流 |
|---|---|---|
| 规则 | 固定、确定性 | 部分步骤靠模型理解自然语言 |
| 输入 | 结构化数据 | 文本、文档、对话、图片等 |
| 灵活性 | 低 | 高（总结、分类、生成、推理） |
| 风险 | 逻辑写死 | 可能幻觉，需要校验节点 |

AI 工作流不是「全自动魔法」，而是 **在可控流程里用 AI 处理不确定环节**。

---

## 典型组成

```text
触发器 → 上下文准备 → AI 处理 → 校验/规则 → 工具调用 → 输出/通知 →（可选）人工审核
```

| 环节 | 做什么 |
|---|---|
| **触发** | 新工单、定时任务、Webhook、用户提问 |
| **上下文** | 拉文档、查库、读历史、RAG 检索 |
| **AI 节点** | 分类、摘要、生成、代码建议 |
| **工具** | 调 API、写数据库、发邮件、创建 PR |
| **分支** | 按置信度/分类走不同路径 |
| **人工** | 低置信度、高风险时人工确认 |
| **观测** | 日志、成本、成功率、反馈回流 |

## 主要应用场景

> 按「解决什么业务问题」归纳；与下文「五种常见模式」互补——模式讲**结构**，本节讲**场景**。

### 按价值链（8 类）

| 场景 | 在做什么 | 典型例子 |
|------|----------|----------|
| **信息获取与整理** | 多源拉取 → 清洗 → 摘要 → 入库 | 竞品监控、政策/技术周报、会议纪要结构化 |
| **内容生产** | 按模板生成初稿，人终审 | 方案、PR 描述、发布说明、培训材料 |
| **代码与工程** | 读代码库 → 改代码 → 跑检查 → 提 PR | 修 CI、补测试、按 issue 改 bug、依赖升级 |
| **分析与决策支持** | 原始数据 → 结论与选项 | 日志/GC 归因、账单异常、需求可行性评估 |
| **流程自动化** | 事件触发 → 多步串联 → 通知/落库 | 工单分类派单、告警初诊、入职 checklist |
| **客服与知识问答** | 知识库回答 + 必要时转人工 | 内部 IT 支持、产品 FAQ、运维 runbook |
| **评审与质检** | 按 checklist 自动扫一遍 | Code Review、安全扫描解读、合规初审 |
| **个人效能** | 固定日常任务助手 | 邮件摘要、待办提取、笔记归档、学习卡片 |

### 按触发方式

| 触发 | 示例 |
|------|------|
| **定时** | 每天 9:00 生成昨日 on-call 摘要 |
| **事件** | PR 创建 → 自动 review；告警 → 自动归因 |
| **人工** | 一键「整理这篇笔记」「生成测试计划」 |
| **对话** | Slack/飞书 @机器人 查 runbook |
| **批处理** | 周末批量处理 500 条工单分类 |

工程里最常见：**事件驱动 + 定时补全 + 人工卡点**。

### 研发场景（详解）

#### 1. 代码维护流

```text
Issue/告警 → 定位相关文件 → 提出 patch → 跑 lint/test → 开 PR → 人合并
```

适合：范围小、验收明确的改动（修 typo、补类型、改配置）。

#### 2. 排查诊断流

```text
gc.log / 慢查询 / 堆栈 → 解析 → 对照知识库 → 输出「可能原因 + 下一步命令」
```

适合：有固定排查套路的领域（JVM、网络、DB）。可双链 [[1000-JVM专题导航]]、[[1004-G1垃圾回收与堆内存]] 等专题笔记作 RAG 上下文。

#### 3. 文档与知识库流

```text
对话/草稿 → 结构化笔记 → 挂到专题导航 → 补交叉链接 → 人确认后入库
```

适合：Obsidian 式专题沉淀——讨论 → 解释 → 「整理」→ 编号笔记 + 导航。

#### 4. CI/CD 与发布流

```text
变更集 → 生成 release note → 检查 breaking change → 通知相关人
```

#### 5. 测试流

```text
需求/接口变更 → 生成用例草案 → 补边界场景 → 人选用例入库
```

### 非研发场景

| 领域 | 工作流示例 |
|------|------------|
| 运营 | 活动数据日报 + 异常解释 + 改投建议草案 |
| 销售 | 客户邮件摘要 + CRM 字段更新建议 |
| HR | 简历初筛 + 面试题生成（需防偏见、人工复核） |
| 法务/合规 | 合同条款对照 checklist（**不能替代律师终审**） |
| 财务 | 发票/报销分类 + 异常标记 |

### 与「单次聊天」的区别

| | 单次聊天 | AI 工作流 |
|--|----------|-----------|
| 触发 | 人想起才问 | 定时/事件自动跑 |
| 上下文 | 靠当次对话 | 固定读知识库/仓库 |
| 输出 | 一段话 | 文件、PR、工单、报表 |
| 质量 | 波动大 | 模板 + checklist 更稳定 |
| 成本 | 低门槛 | 前期搭链路，后期省时间 |

### 知识库沉淀示例（本仓库实践）

```text
专题讨论（如 G1 / ZGC / TLAB）
  → AI 详细解释
  → 用户说「整理」
  → 写入编号笔记（100x）+ 专题导航（1000）+ 交叉链接
```

可扩展的固定工作流：

1. **新告警 → 对照 JVM 专题 → 输出排查清单**
2. **每周技术摘要 → 判断是否补进知识库**
3. **PR 涉及 GC 参数 → 对照工程实践 checklist**
4. **面试前 → 按专题导航生成复习题**

## 五种常见模式

### 1. 链式（Chain）

```text
用户问题 → 检索知识库 → LLM 回答 → 格式化输出
```

步骤固定，适合 FAQ、固定 RAG。

### 2. 路由（Router）

```text
工单 → AI 判类型（技术/商务/投诉）→ 分别走不同处理链
```

省成本：简单问题不走大模型全套。见 [[AI/00-AI学习体系/02-概念库/01-模型层/08-Model Routing|Model Routing]]。

### 3. 并行（Parallel）

```text
竞品资料 → 并行：价格 + 功能 + 风险 → 合并成报告
```

### 4. 人机协同（Human-in-the-loop）

```text
AI 生成回复 → 客服确认 → 发送给客户
```

### 5. Agent 式（多步自主）

```text
目标：查生产故障 → 查日志 → 查 DB → 给结论
```

模型自己决定下一步；需 **步数上限、权限白名单**。见 [[AI/00-AI学习体系/02-概念库/03-Agent系统/02-ReAct与Agent范式|ReAct与Agent范式]]。

## 开发向示例：代码评审辅助

```text
1. 触发：PR 创建
2. 拉取 diff + 相关模块文档（RAG）
3. LLM：安全/性能/规范检查
4. 规则引擎：必须通过项（测试、lint）
5. 输出：评审意见草稿
6. 人工：工程师最终 merge
```

## 搭建方式

| 方式 | 适合谁 | 代表 |
|---|---|---|
| **可视化编排** | 产品、运营、快速验证 | Dify、Coze、n8n + LLM |
| **代码编排** | 研发、深度定制 | LangGraph、LangChain、DSPy |
| **平台内置** | 已有业务系统 | 飞书/钉钉 AI、各云 Agent 平台 |

## 做好 AI 工作流的六条原则

1. **任务拆小**：一个节点只做一件事（分类、摘要、生成分开）
2. **上下文可控**：限定输入、必要时 RAG；见 [[AI/00-AI学习体系/02-概念库/06-工程生态/02-Context Engineering|Context Engineering]]
3. **输出结构化**：JSON / 固定模板，方便下游处理
4. **设兜底**：超时、解析失败、低置信度 → 转人工或重试
5. **可观测**：记录 prompt、token、耗时、反馈
6. **权限与安全**：工具调用、DB、生产操作要白名单

## 适合 / 不适合的场景

> 场景全景见上文 **「主要应用场景」**；下表为快速判断。

| 适合 | 不太适合 |
|---|---|
| 客服分类与初回复 | 强实时、零容错纯计算 |
| 文档摘要、周报 | 无审计要求的随意聊天 |
| 代码审查草稿 | 只靠 LLM 自评就上线的合规场景 |
| 非结构化信息抽取 | 一次性战略决策、输入极模糊 |
| 内部知识库问答（RAG） | |
| 运维告警**初步**分析（需权限） | |
| **重复、结构化、可验收**的知识劳动 | |

## 与 Graph、Loop、Agent 的关系

```text
AI 工作流（业务层）
  └─ Graph（结构层）：节点 + 边 + State
       └─ Loop（控制层）：某几步是否反复执行
            └─ Agent：Loop 里由 LLM 决定走哪条边
```

| 概念 | 更贴近 |
|---|---|
| **Graph** | 工作流骨架 |
| **Loop** | 重试、反思、多轮改进 |
| **Agent** | 路径不确定时的自主决策 |

**不是二选一**：常见做法是 **Workflow 包 Agent**（外壳可控，中间一段开放推理）。

## 选型口诀

```text
步骤清楚、要审计、要上线     → Workflow
步骤多、要可视化调试          → Graph 编排（LangGraph / Dify）
某步要反复试直到达标          → 规则 Loop（仍 Workflow）
路径不确定、工具多            → Agent（外面再套 Workflow 约束）
```

90% toB：**Workflow + 可选规则 Loop** 即可；见 [[AI/00-AI学习体系/02-概念库/03-Agent系统/01-Workflow vs Agent|Workflow vs Agent]]。

## 自评与验收

工作流里常用「生成 → LLM 自检 → 不满意再改」的 Loop，但**不能单靠 LLM 说「满意了」就结束**。

原因与做法见 [[AI/00-AI学习体系/02-概念库/05-评测/03-LLM-as-a-Judge|LLM-as-a-Judge]] 中「工作流中的自评与硬校验」一节。
